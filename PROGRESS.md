### 1.3. Окружение рабочей машины (03.11.2026) — важно

**Путь проекта — только латиницей.** Переехали из `C:\DeepSeek_Projects\ДомКруг`
в `C:\Projects\domkrug`. Причина: PostgreSQL 16 на Windows 10 падает на
кириллических путях (`invalid byte sequence for encoding "UTF8": 0xc4 0xee`),
а `initdb` не может сменить права вне профиля пользователя.

| Что | Где |
|---|---|
| Код | `C:\Projects\domkrug` |
| PostgreSQL 16.9 (бинарники, кластер, лог) | `C:\domkrug-pg` |
| Скрипты запуска базы | `scripts\db-start.ps1`, `db-stop.ps1`, `db-status.ps1` |
| Git | 2.56.0, репозиторий инициализирован, `origin` = GitHub |

**Docker Desktop теперь работает (29.9.2, linux) — база поднята в контейнере.**
Что понадобилось: VT-x в BIOS, компоненты `VirtualMachinePlatform` и
`Microsoft-Windows-Subsystem-Linux`, и обновление самого WSL (`wsl --update` → 3.0.1).
Перезагрузка после этого не потребовалась.

**Проверено оба способа запуска базы, результат одинаковый — 100/100:**

| Способ | Команда | Миграции + сид | Тесты |
|---|---|---|---|
| Docker (сейчас) | `docker compose up -d postgres` | ✅ | ✅ 34 + 25 + 41 |
| Нативно | `scripts\db-start.ps1` | ✅ | ✅ 34 + 25 + 41 |

`scripts\db-status.ps1` теперь показывает, **откуда** взята база — из Docker или нативная.

**`docker compose up -d` целиком пока не проходит — MinIO удалён с Docker Hub.**
Образ `minio/minio` больше не публикуется, а `quay.io/minio/minio` требует
авторизации. Это не наша поломка: тот же сбой у Apache Flink, Carbynestack,
objectfs. Обход: поднимать только базу — `docker compose up -d postgres`.
Решение по MinIO отложено до момента, когда понадобятся фото заявок
(эндпоинта `/attachments` ещё нет). Варианты записаны в `docs/DECISIONS.md`.

### 1.4. Лимиты запросов в development (актуальное состояние)

**Было:** чтобы тесты с одного IP не упирались в лимит входа 10/мин, лимиты
в development **отключались** через `allowList: () => true`.

**Стало (03.11.2026, вечер):** отключение убрано. В `backend/src/lib/limits.ts`
функция `scaledLimit()` умножает лимит на 50 в development — механизм работает
и проверяется, а тесты не упираются. Заодно CORS в development ограничен
`http://localhost:5173` вместо `origin: true`, и при старте в непроизводственном
режиме пишется предупреждение в лог. Подробнее — `docs/DECISIONS.md`.

**Почему отключение было плохим:** невыполняемый в разработке код проверяется
только в production, то есть на живых пользователях.

**Две ловушки, на которых я споткнулся — чтобы не повторить:**

1. **Проверка 375px.** Chromium на Windows не даёт окно уже ~500px, поэтому

   Правильно — мерить внутри `iframe` шириной 375px. При первом замере
   «через окно» я едва не принял артефакт браузера за дефект вёрстки.
2. **Кодировка.** Перезапись `.tsx` через PowerShell (`Get-Content -Raw` +

   как ANSI. Файлы восстановлены перезаписью; проверка — 0 файлов с BOM.
   **Правило: файлы проекта править инструментом записи, не через PowerShell.**

**Не сделано (следующие шаги плана):** PWA-манифест (шаг 8),
создание заявки диспетчером «от имени жителя» (`/tickets/new`).

### 1.7. Фронтенд — шаг 3, создание заявки (03.11.2026)

| Файл | Что делает |
|---|---|
| `src/pages/resident/TicketCreatePage.tsx` | Форма: категории, срочность, описание, контакт |
| `src/components/TextArea.tsx` | Многострочное поле со счётчиком символов |
| `src/lib/useCategories.ts` | Справочник категорий (`GET /ticket-categories`) |

**Решения, которые стоит помнить:**

- **«Аварийная» ставится по категории, а не на выбор жителя.** Если человек сам
  выбирает «аварийно», это пишут про всё подряд, и красная метка в инбоксе
  перестаёт что-либо значить. Категории «Лифтовое оборудование»,
  «Электроснабжение», «Отопление» помечены на сервере как аварийные
  (`is_emergency`), SLA по ним 4–8 часов — приоритет выставляется автоматически.
- **Описание минимум 10 символов** — проверка и на клиенте, и в схеме сервера.
- **Телефон подставляется из профиля**, формат `+7XXXXXXXXXX` (та же регулярка,
  что в `backend/src/modules/tickets/routes.ts`).
- **После отправки — отдельный экран успеха с номером**, а не переход на
  карточку: карточки (шаг 5) ещё нет, а вести в заглушку — плохо.
- **403 `BINDING_NOT_CONFIRMED`** во время отправки (привязку отозвали с момента
  открытия формы) ведёт на главную, где уже объяснено, что делать.

**Проверено интерактивно, не только по коду.** Через DevTools Protocol (CDP)
заполнил форму и нажал «Отправить»: категория выбрана, срочность «Высокая»,
поля заполнены, кнопка нажата → экран «Заявка отправлена №13». Заявка
появилась в инбоксе диспетчера с заголовком, категорией и приоритетом `high`.
Отдельно проверено: аварийная категория даёт `priority=emergency` и SLA 4 часа,
попадает в фильтр «аварийные».

Это первый случай, когда проверка идёт настоящим кликом по настоящему DOM —
для многошаговых форм скриншота недостаточно.

### 1.8. Фронтенд — шаги 5 и 6, карточка заявки (03.11.2026)

| Файл | Что делает |
|---|---|
| `src/pages/TicketPage.tsx` | Карточка заявки: данные, действия по правам, комментарии |
| `src/pages/TicketPage.module.css` | Стили карточки |
| `src/lib/useTicket.ts` | Загрузка одной заявки; путь выбирается по роли |

**Один экран на все роли.** Набор кнопок строится по правам, а не по названию
роли: админ УК, который сам живёт в доме, должен видеть и то, и другое.
Настоящая проверка всё равно на сервере — клиент лишь не показывает лишнего.

**Действия по статусу:**

| Статус | Кто | Что видит |
|---|---|---|
| `new` | диспетчер/админ | Принять · Назначить · Отклонить |
| `accepted` | диспетчер/админ | Назначить · Отклонить |
| `assigned` | исполнитель | Взять в работу |
| `in_progress` | исполнитель | Ожидает материалов · Отметить выполненной · Закрыть |
| `waiting` | исполнитель | Возобновить · Отметить выполненной · Закрыть |
| `done` | исполнитель/админ | Закрыть |
| `closed` | житель | «Проблема не решена» → новая заявка со ссылкой |

Диспетчер кнопки «Закрыть» не видит вообще: закрывает тот, кто выполнил работу
(PROGRESS.md п. 5.1, RBAC.md п. 4.4).

**Сквозной сценарий прогнан целиком в браузере через CDP:**
принять → назначить Петрова → переназначить → (исполнитель) взять в работу →
закрыть с описанием работ → (житель) «Проблема не решена» → создана заявка
«Повторное обращение» со ссылкой на исходную.

Подтверждено отдельно:

- **Телефон жителя скрыт от исполнителя после закрытия** — сервер отдаёт
  `contactPhone: null`, карточка показывает «скрыт». Это требование
  `DB-SCHEMA.md`, а не случайность.
- **Служебный комментарий не виден жителю.** Диспетчер добавил с пометкой
  «Служебный» → у жителя блок комментариев пуст, проверено по тексту страницы.
- **Общедомовая заявка недоступна жителю** (404): заявка №6 про лифт не
  привязана к квартире, и `getTicketForResident` её не отдаёт. Так и задумано.

**Найден и исправлен баг в клиенте API.** `toApiError` заменял любой 429 на
«Слишком много запросов», из-за чего терялось объяснение сервера «по этой
заявке уже создано повторное обращение, подождите сутки». Теперь общие тексты
подставляются только если сервер ничего не сказал.

### 1.9. Фронтенд — шаг 7, привязка квартиры (03.11.2026)

| Файл | Что делает |
|---|---|
| `src/pages/BindingPage.tsx` | Житель: свои привязки, поиск квартиры, заявка, отзыв |
| `src/pages/staff/BindingsPage.tsx` | УК: очередь заявок, подтверждение, отклонение с причиной |
| `src/lib/useBindings.ts` | Два хука: своя выборка и очередь УК |
| `src/pages/BindingPage.module.css` | Стили обеих страниц |

**Что учтено:**

- **Поиск отдаёт только адрес, номер квартиры и название УК.** Ни ФИО, ни
  телефонов, ни истории — это ограничение сервера, и оно правильное: иначе
  поиск стал бы способом разведки по чужим квартирам.
- **Минимум 3 символа** в адресе — та же проверка, что в схеме сервера
  (`searchSchema`), иначе поиск по «1» вернул бы весь город.
- **Подтверждать может диспетчер, а не только админ** — на пилоте он
  единственный, кто постоянно на связи (RBAC.md п. 4.3).
- **Отклонение требует причины, и житель её видит.**

**Найден и исправлен дефект на сервере.** В `getBindings`
(`backend/src/modules/auth/service.ts`) не выбирался `reject_reason`, поэтому
житель не мог узнать, почему УК отклонила привязку, — при том что в форме
отклонения было написано «Житель увидит причину». Это была неправда в
интерфейсе. Поле добавлено в выборку и в `BindingView`, причина выводится
в карточке привязки. API-тесты после правки: 100/100.

Заодно исправлена вёрстка: блок причины отклонения растягивал левую колонку
и выталкивал статус из правого верхнего угла вниз. Теперь причина идёт
отдельной строкой под верхней частью карточки.

**Проверено в браузере через CDP:** житель ищет «Ленина», видит 9 квартир,
отправляет заявку на кв. 7 → у диспетчера в очереди 2 заявки → подтверждает
кв. 5 и отклоняет кв. 7 с причиной → у жителя кв. 5 «Подтверждена»,
кв. 7 «Отклонена» с текстом причины.

- **Service worker только в собранном приложении.** В разработке он кеширует

- **API не кешируется вообще.** Данные заявок персональные и быстро устаревают;

- **Переходы по страницам — сначала сеть**, при обрыве оболочка из кеша.
  Так после деплоя пользователь сразу получает свежую версию, а не старую
  из кеша.
- **Иконки рисуются скриптом, а не лежат готовыми файлами.** Цвет берётся
  из палитры; если бренд поменяется, иконки пересобираются одной командой,
  а не ищутся в архиве.

### 1.11. Заявка от диспетчера «от имени жителя» (03.11.2026)

| Файл | Что делает |
|---|---|
| `src/pages/staff/NewTicketPage.tsx` | Форма: источник, дом, квартира, категория, срочность, контакт |
| `src/lib/useBuildings.ts` | Дома УК и квартиры выбранного дома |

**Зачем это нужно.** Не все жители пользуются приложением. Срочный звонок
нельзя терять только потому, что человек не зарегистрирован (ТЗ v1.1 п. 3.2,
PROGRESS.md п. 5.2).

**Чем отличается от формы жителя:**

- дом и квартиру выбирает сотрудник, а не берётся подтверждённая привязка;
- обязателен **источник** обращения: `dispatcher_phone` или `dispatcher_walkin` —
  чтобы потом было видно, откуда пришла заявка;
- есть **контактное лицо** — как житель представился по телефону;
- **квартиру можно не указывать** — обращения по подъезду, крыше, двору
  относятся к местам общего пользования;
- **диспетчер может сразу поставить «Аварийная»**. Жителю это право не даём
  (там приоритет выводится из категории), а диспетчеру нужно: он и так обязан
  реагировать на аварию, и ждать, пока человек выберет категорию, некогда.

**Проверено в браузере через CDP:** заполнил форму (по телефону, дом, квартира,
категория, «Аварийная», описание, контакт «Сидоров, кв. 12», телефон) →

### 1.12. Регистрация жителя (03.11.2026)

| Файл | Что делает |
|---|---|
| `src/pages/RegisterPage.tsx` | ФИО, телефон, e-mail, пароль, согласие на ПДн |
| `src/lib/auth.tsx` | `register()` в провайдере: сервер сразу выдаёт сессию |
| `src/lib/authContext.ts` | `loginError`/`isLoggingIn` → `authError`/`isSubmitting` |

**Зачем.** До этого нового жителя нельзя было завести через интерфейс — только
войти существующим. Сценарий «зарегистрировался → привязался → создал заявку»
рвался на первом шаге, а показывать УК такое нельзя.

**Что важно в реализации:**

- **Согласие на обработку ПДн не предустановлено и обязательно** (152-ФЗ).
  Согласие «по умолчанию включено» согласием не является. Факт согласия сервер
  пишет в `audit_log` с версией текста — проверено: `{"consentAccepted": true,
  "consentVersion": "1.0"}`.
- **Повтор пароля проверяется на клиенте** — на сервер уходит один пароль.
  Это UX, а не безопасность: опечатку в пароле иначе не увидеть.
- Телефон обязателен, e-mail — нет: у жителя чаще есть телефон.
- После успеха человек уже авторизован (сервер выдаёт сессию вместе с 201)
  и попадает сразу на привязку квартиры.

**Найден и исправлен дефект маршрутизации.** `/register` был обёрнут в
`RequireGuest`, который при появлении авторизации уводит на `/`. Из-за этого
после регистрации человек оказывался на главной с «адрес не привязан», а не на
экране привязки. Обёртку с регистрации сняли: страница сама решает, куда идти.

**Проверено в браузере через CDP, всю цепочку нового человека:**
заполнил форму (ФИО, телефон, e-mail, пароль, согласие) → аккаунт создан,
открылся экран «Квартира» → поиск «Ленина», заявка на привязку → диспетчер
подтвердил → на главной появился адрес и активная кнопка «Создать заявку».
Заодно проверено, что повторная регистрация с тем же телефоном даёт 409.

### 1.13. Приведение телефона к единому виду (03.11.2026)

**Проблема от владельца:** люди пишут номер как привыкли — `8-923…`, `+7923…`,
`7923…`, просто `923…`. Сервер ждёт строго `+7` и 10 цифр, поэтому половина
вводов не проходила валидацию, а на экране входа номер просто не находился.

| Файл | Что делает |
|---|---|
| `src/lib/format.ts` | `normalizePhone()` — 11 цифр с 7/8 → `+7…`; 10 цифр с 9 → `+7…` |
| `src/lib/format.test.ts` | 9 тестов: все варианты ввода, e-mail, незаконченный ввод |
| Вход, регистрация, заявка жителя, заявка диспетчера | нормализация на blur и перед отправкой |

**Решения:**

- **Нормализация по уходу из поля (blur), а не на каждом нажатии.** Переписывать
  номер под курсором во время набора — значит дёргать курсор у человека,
  который и так печатает медленно.
- **Нормализуем ДО проверки формата**, иначе `8-923…` показывался бы как ошибка,
  хотя номер правильный.
- **E-mail не трогаем**: на экране входа одно поле принимает и телефон, и e-mail.
- **Не угадываем двусмысленное.** 10 цифр без семёрки и без девятки в начале
  (`3831234567`) остаются как есть: непонятно, есть ли код страны.
- **Городской с семёркой нормализуется** — `+7 (383) 123-45-67` и `+73831234567`
  один и тот же номер, скобки к нему не относятся.

**Тест поймал мою собственную ошибку.** Я написал в тесте, что городской номер
превращать нельзя, — и он упал: `+7 (383) 123-45-67` → `+73831234567`. Прав
оказался код, а не тест: это тот же номер без форматирования. Ожидание
исправлено, правило задокументировано.

**Проверено вживую:** в форме регистрации все четыре вида дают `+79231234567`;
e-mail не меняется. Сквозной случай: регистрация с `8 923 777 88 99` → в поле
`+79237778899` → вход тем же аккаунтом через `923 777 88 99` → успешно.
`npm run test` — 9 тестов зелёные.

### 1.16. Ревизия модели статусов (03.11.2026)

Владелец разобрал модель по кнопкам и нашёл нестыковки. Решения и правки:

**Решение владельца: вариант A — «Выполнена» убирается из рабочего потока.**
Исполнитель закрывает заявку сразу, с описанием работ. Промежуточный статус
`done` остался в базе для совместимости, но кнопки «Отметить выполненной» в
интерфейсе больше нет. Это согласуется с решением C из раздела 5.1
(житель не подтверждает выполнение).

| Что было не так | Что сделано |
|---|---|
| На «Выполнена» висели «Переназначить» и «Отклонить» | скрыты в интерфейсе **и запрещены на сервере** |
| Переназначение выполненной возвращало статус в «Назначен» и стирало факт работ | сервер отвечает 409 «Работы уже выполнены» |
| Выполненную заявку можно было «отклонить» | сервер отвечает 409 «Отклонить её нельзя» |
| Назначение обходило таблицу переходов и не ставило время принятия | `accepted_at` заполняется автоматически (`COALESCE`) |

**Почему назначение = принятие.** Диспетчер не может отдать заявку, не
отреагировав на неё. Раньше при назначении прямо из «Новой» `accepted_at`

стала необязательной: она нужна для случая «взял в обработку, исполнителя
назначу позже».

**Что осталось на потом (приоритет 2):** переименовать «Принять заявку» в
«Взять в обработку» — сейчас оно путается с «Взять в работу» у исполнителя.

**Известный край:** заявки, оставшиеся в «Выполнена» от прежних прогонов,
диспетчер закрыть не может — у него нет права `ticket.close` (так и задумано).
Закрывает исполнитель или админ. В новом потоке такие заявки не появляются.

### 1.18. Закрытие заявки назначенным исполнителем (03.11.2026)

### 1.23. Конец проблем с кириллицей: убрали границы, а не симптомы (03.11.2026)

**Проблема была системной.** Кириллица ломалась не «вообще», а на границах,
где строка превращается в байты. В Windows PowerShell 5.1 у каждой границы
свой дефолт из 1990-х: файл без BOM читается как ANSI, тело запроса
кодируется в ANSI, аргументы процесса — в OEM cp866, вывод — в cp866.

Правило в документации («отправляй UTF-8») не работало, потому что требовало,
чтобы каждый новый скрипт кто-то не забыл написать правильно.

**Что сделано:**

| Мера | Файлы |

### 1.24. Живые обновления: заявки и уведомления без перезагрузки (05.11.2026)

**Задача от владельца:** новые заявки у диспетчера и изменения у жителя должны
появляться сами; такие же места будут находиться и дальше, поэтому нужно общее
решение, а не заплатки. Плюс колокольчик с переходом в заявку.

**Выбор транспорта — опрос, а не WebSocket/SSE.** Причина не в лени:
- токен доступа живёт в памяти вкладки, а `EventSource` не умеет отправлять
  заголовок `Authorization` — пришлось бы менять авторизацию ради одного канала;
- refresh-cookie привязана к пути `/api/v1/auth`, для потока её пришлось бы
  расширять до всего API;
- на пилоте с несколькими пользователями опрос раз в 5 секунд дешевле:
  нет долгоживущих соединений, нечему рваться при перезапуске службы.

Реализовано ровно так, чтобы транспорт можно было заменить позже, не трогая
экраны: страницы не опрашивают ничего сами, они подписаны на счётчик изменений.

| Слой | Что сделано |
|---|---|
| `GET /api/v1/updates` | отпечаток: сколько заявок, когда последняя менялась, последнее событие доступа, непрочитанные уведомления |
| `GET /api/v1/notifications` | лента + общий счётчик непрочитанных (не только в странице) |
| `POST /notifications/:id/read`, `/read-all` | отметка прочтения; чужое — 404, как несуществующее |
| Уведомление УК | о новой заявке жителя (всем диспетчерам и админам УК, кроме автора) |
| Уведомление жителю | об ответе УК; об исполнителе — о сообщении жителя |
| `UpdatesProvider` | один опрос на всё приложение, пауза на скрытой вкладке, мгновенное обновление при возврате |
| `NotificationBell` | колокольчик со счётчиком, лента, клик ведёт в заявку; закрытие по Escape и клику вне |
| Хуки | `useTicketList`, `useTicket`, `useTicketHistory`, `useAccessEvents` сами перезапрашивают данные по сигналу |

**Важная деталь реализации.** Сигнал передаётся счётчиком в зависимостях
эффекта, но **не** входит в ключ запроса. Иначе `loading` становился бы `true`
на каждом опросе и список мигал бы «Загружаем…» каждые пять секунд.

**Проверено в браузере (не только тестами):**
- инбокс диспетчера: была 18 заявок → создал заявку жителем → через 5 секунд
  стало 19, счётчик колокольчика 1 → 2, страница **не перезагружалась**;
- житель: ответ УК по заявке пришёл в колокольчик, клик по строке открыл
  нужную заявку (`/my-requests/<id>`);
- мобильная ширина 430px: колокольчик на месте, панель не вылезает.

**Тесты:** +6 API-тестов (доставка адресату, отметка прочтения, чужое — 404,
`read-all`, разная область видимости в `/updates`, 401 без авторизации).
Всего 72 проходят.

**Что осталось на потом:** тот же сигнал легко подключить к счётчикам, лифтам
и сообщениям УК — это одна строка в соответствующем хуке. Список таких мест
владелец будет пополнять.

**Важно про деплой.** Живые обновления работают только там, где развёрнут
новый код. 05.11 владелец проверял с телефона на `https://1brn.ru` и не видел
ни уведомлений, ни новых заявок — причина не в коде: на сервере была сборка
от 04.11. Проверка: `curl -s https://1brn.ru/api/v1/updates` отвечал **404**,
а локально тот же адрес — **401** (эндпоинт есть, нужен вход).

Чтобы это не выглядело загадкой, провайдер теперь пишет в консоль браузера
`[updates] опрос не удался` (один раз на каждое сообщение, без спама).

**После обновления сервера подсказка демо-входов пропадёт**, если собирать
обычным `npm run build`: пароль задаётся только переменной `VITE_DEMO_LOGINS`

### 1.25. Доступ к серверу для деплоя: почему root по SSH не пускает (05.11.2026)

Живые обновления заработали на проде только после деплоя. По дороге потратили
несколько часов на доступ — записываю, чтобы второй раз не искать.

**Симптом.** Ключ добавлен в панели Timeweb, но вход даёт
`Permission denied (publickey)`. При этом в подробном логе видно
`Server accepts key` — то есть sshd **нашёл** ключ и согласился с ним.

**Что исключили по очереди:** ключ доходит до сервера (сервер его принимает);
клиент исправен (Windows OpenSSH 9.5 и Git OpenSSH 10.6 ведут себя одинаково);
ожидание не помогает (6 попыток за 2 минуты); панель пишет правильно (второй,
новый ключ тоже принят); `faillock` не виноват (сброс и перезапуск sshd не
помогли).

**Причина.** В `journalctl -u ssh` по нашему IP:

```
ROOT LOGIN REFUSED FROM 37.205.81.67 [preauth]
```

Сервер **запрещает вход root по SSH** на уровне PAM. Ключ проверяется успешно,
а следующий шаг — проверка учётной записи — отвечает отказом.

Отдельно важно: **SSH-пароль на сервере выключен полностью** (`PreferredAuthentications=none`
→ `Permission denied (publickey)`), поэтому пароль root для SSH бесполезен —
он работает только в веб-консоли Timeweb.

**Решение (и оно правильное по безопасности):** не разрешать root, а завести
пользователя `deploy`:

```bash
adduser --disabled-password --gecos "" deploy
mkdir -p /home/deploy/.ssh && chmod 700 /home/deploy/.ssh
echo '<публичный ключ>' > /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys && chown -R deploy:deploy /home/deploy/.ssh
echo 'deploy ALL=(ALL) NOPASSWD:ALL' > /etc/sudoers.d/deploy && chmod 440 /etc/sudoers.d/deploy
```

`/srv/domkrug` уже принадлежит `deploy`, поэтому `git pull` работает без sudo.

**На будущее — проверять доступ одной командой:**

```bash
journalctl -u ssh --since "-15 min" --no-pager | grep <ваш IP>
```

Строка `ROOT LOGIN REFUSED` сразу говорит, что дело не в ключе, а в политике
входа. Без этого фильтра лог бесполезен: боты занимают все последние строки.

**Деплой выполнен 05.11**, скрипт лежит в `scripts/deploy.sh`: бэкап базы →
`git pull` → миграции → сборка бэкенда и фронтенда → перезапуск → проверки.
Запуск: `bash /tmp/liviti_deploy.sh` (копируется по `scp`).

**Проверено на проде после деплоя:**
`/api/v1/updates` → 401 (было 404); житель создал заявку №19; у диспетчера
счётчик непрочитанных 7 → 8, первая запись «Новая заявка №19».

**Моя ошибка при настройке доступа.** Записывая свой ключ, я использовал
`echo '…' > /home/deploy/.ssh/authorized_keys`. Знак `>` **перезаписывает**
файл, и ключ домашней машины (отпечаток `SHA256:coW9pGP…`, входил под `deploy`
4 ноября) исчез. Залогиниться с дома по ключу больше нельзя.

Что сделано, чтобы это не повторилось:
- перед правкой `authorized_keys` теперь делается копия, а cron в 04:05 держит
  `authorized_keys.daily.bak`;
- в `docs/SERVER-ACCESS.md` и в начале `START-HERE.md` записано правило:
  только `>>`, сначала посмотреть содержимое, после правки проверить вход
  **старым** ключом;
- восстановление домашнего ключа расписано по шагам (нужна веб-консоль и
  публичная часть ключа с домашней машины).

**Как быстро понять причину отказа — три команды:**

```bash
curl -s https://ifconfig.me/ip                                   # свой IP
journalctl -u ssh --since "-15 min" --no-pager | grep <IP>       # что сказали именно нам
cut -d' ' -f3 /home/deploy/.ssh/authorized_keys                  # какие ключи лежат
```

Без фильтра по IP лог бесполезен: боты занимают все последние строки.

### 1.26. Переезд на liviti.ru, 1brn.ru — постоянный редирект (05.11.2026)

**Задача владельца:** основной адрес — `liviti.ru`, прежний `1brn.ru`
перенаправляет на него.

**Что изменено на сервере:**

| Где | Было | Стало |
|---|---|---|
| `/etc/caddy/Caddyfile` | блок `1brn.ru` отдаёт сайт, `:80` — аварийный вход | `liviti.ru` отдаёт сайт; `www.liviti.ru`, `1brn.ru`, `www.1brn.ru` → `redir … permanent`; аварийный вход по IP сузился до `http://198.51.100.10` |
| `/srv/domkrug/.env` | `APP_URL=https://1brn.ru` | `APP_URL=https://liviti.ru` |
| `MembersPage.tsx` | текст «Вход: 1brn.ru» зашит строкой | подставляется `window.location.host` |

**Почему аварийный вход сузился до IP.** Раньше блок `:80` перехватывал все
HTTP-запросы, включая запросы к доменам, — домены не получали автоматический
переход на HTTPS. Теперь `:80` занят только автоматическим редиректом Caddy, а
аварийный вход доступен по `http://198.51.100.10`.

**Почему сначала 302, а потом 301.** `permanent` (301) браузеры кешируют
надолго: если бы что-то пошло не так, откатить перенаправление у сотни
тестировщиков нельзя — они уже не спросят сервер. Поэтому сначала подняли
`temporary`, проверили все четыре адреса, и только потом одной правкой
переключили на `permanent`.

**Проверено снаружи (curl, без следования редиректам):**

```
https://liviti.ru                         → 200
https://www.liviti.ru                     → 301 https://liviti.ru/
https://1brn.ru                           → 301 https://liviti.ru/
https://1brn.ru/tickets/12?tab=history    → 301 https://liviti.ru/tickets/12?tab=history
https://liviti.ru/api/v1/updates          → 401 (API живёт на новом домене)
```

**Проверено приложение на новом домене:** вход диспетчером → 200, `/auth/me`
отдаёт роли и УК, `/api/v1/notifications` отвечает; `POST /auth/refresh` по
cookie выдаёт новый токен — значит refresh-cookie корректно привязана к
`liviti.ru`.

**Что знает владелец:** у всех, кто был в системе на старом домене, сессии
слетят — cookie привязана к домену, войти нужно заново. Установленное PWA с
`1brn.ru` придётся поставить заново с нового адреса (manifest использует
относительные пути, поэтому на новом домене работает сразу).

**Откат:** `/etc/caddy/Caddyfile.before-liviti` (и `.before-permanent`),
`/srv/domkrug/.env.before-liviti`.

### 1.27. Приём звонков с вызывной панели (AMI), 06.11.2026

**Задача:** чтобы звонок с панели всплывал окном у жителя, а не создавался
кнопкой «Смоделировать звонок».

**Почему AMI, а не вебхук.** Дмитрий проверил на живом железе
(`docs/INTERCOM-HIKVISION.md`, раздел 3): событие нажатия кнопки вызова у
Hikvision по HTTP не отдаётся никак — ни `alertStream` (там только события
доступа), ни `callStatus` (остаётся `idle`), ни `httpHosts` (адрес
сохраняется, панель по нему не стучится). Единственный источник —
**Asterisk**, который видит вызов и отдаёт его по AMI на `127.0.0.1:5038`.

| Что добавлено | Где |
|---|---|
| Миграция | `018_intercom_ami.sql`: `apartments.intercom_room`, `intercom_calls.ami_unique_id`, типы уведомлений `intercom_call` |
| Разбор потока | `modules/intercom/ami-parser.ts` — чистые функции, 13 тестов |
| Соединение | `modules/intercom/ami-client.ts` — TCP, логин, переподключение с растущей паузой |
| Логика | `modules/intercom/service.ts` — событие → запись звонка + уведомление; `Hangup` → закрытие |
| Настройки | `AMI_ENABLED/HOST/PORT/USER/PASSWORD`, по умолчанию выключено |

**Ключевые решения:**

- **Комната, а не квартира.** Панель набирает номер комнаты, он хранится в
  `apartments.intercom_room`. Не нашли комнату — звонок не создаём: фантомное
  «звонят в никуда» хуже, чем отсутствие записи.
- **Одно событие — один звонок.** Реагируем только на `Newchannel` в контексте
  `from-panel`: Asterisk присылает ещё `Newstate` и `Dial`, и реакция на все
  дала бы три звонка в журнале.
- **Завершение по `Uniqueid`.** Иначе при двух параллельных вызовах
  закрывался бы «последний».
- **AMI выключен по умолчанию** и включается только при заполненных учётке и
  пароле: иначе бэкенд стучался бы в закрытый порт и засорял журнал.

**Дефект, пойманный проверкой, а не в проде.** На один звонок создавалось
**19 уведомлений**: представление `apartment_rights` отдаёт строку на каждую
точку доступа квартиры. Исправлено `SELECT DISTINCT user_id`. Напоминание:
подобные INSERT ... SELECT надо проверять на дубли, а не на «одну строку».

**Проверено сквозным прогоном на локальной базе** (событие подано напрямую в
обработчик, без Asterisk):

```
звонок из 6001 в комнату 100 → квартира …          запись: ringing
уведомлений создано: 1 (intercom_call)
повтор того же события → записей: 1 (дубля нет)
Hangup → статус missed, ended_at заполнен
звонок в комнату 999 → «квартира не найдена», записей: 0
```

**Фронтенд править не пришлось:** `GET /resident/video/intercom/active` уже
читает `intercom_calls` со статусом `ringing`, а окно `IntercomCallOverlay`
опрашивает его раз в 5 секунд. То есть запись, созданная из AMI, появляется
у жителя сама.

**Что осталось:** получить от Дмитрия учётку AMI, номер комнаты стенда и
привязку «комната → квартира», включить `AMI_ENABLED` на сервере. До этого
код живёт в проде выключенным и ни на что не влияет.

### 1.30. Видео со звонка: медиасервер готов (06.11.2026)

**Задача:** в окне звонка показывать картинку с панели. Решение владельца —
видео нужно, запись не нужна.

**Почему go2rtc, а не WebRTC-клиент.** Браузер не понимает RTSP. go2rtc
забирает RTSP и отдаёт **mp4 по HTTP** — такой URL играет в обычном `<video>`
без библиотек. HLS потребовал бы `hls.js`, WebRTC — отдельного плеера и TURN.
Для домофона задержка около секунды приемлема.

| Что | Где |
|---|---|
| Установка | `scripts/install-go2rtc.sh` (идемпотентный) |
| API медиасервера | `127.0.0.1:1984`, наружу — только Caddy по `/go2rtc/*` |
| Источник | `rtsp://<admin>:<пароль>@127.0.0.1:18083/Streaming/Channels/101` (туннель) |
| Пароль | `/etc/go2rtc/panel.env` (600 root), в конфиг и в список процессов не попадает |
| Камера у звонка | AMI-обработчик сразу пишет `camera_id` камеры точки (`kind='call_panel'`) |

**Решения и ловушки:**

- **WebRTC выключен намеренно** (`webrtc: listen: ""`): иначе go2rtc открывает
  8555/udp в интернет, а нам нужен только mp4 через HTTPS.
- **`handle_path`, а не `handle`** в Caddy: с `handle` префикс `/go2rtc` не
  отрезался, и go2rtc отвечал 404. Поймано проверкой, а не в проде.

**Проверено:** API медиасервера доступен через `https://liviti.ru/go2rtc/api/streams`
(200), звонок приходит с привязанной камерой «Вызывная панель подъезда 1».
Попытка забрать поток отвечает `streams: wrong user/pass` — то есть **сеть и
туннель работают, панель отвечает отказом только из-за пустого пароля**.

**Что осталось:** вписать пароль панели в `/etc/go2rtc/panel.env`, перезапустить
службу, затем у камеры поставить `stream_type='webrtc'` и
`stream_url='https://liviti.ru/go2rtc/api/stream.mp4?src=panel'`. До этого в
окне показывается демо-заставка.

### 1.32. Почему окно звонка появлялось через 60 секунд (06.11.2026)

**Причина найдена на панели, а не в приложении.** Настройка «приоритет вызова»
(`GET /ISAPI/VideoIntercom/callPriority?format=json`):

```json
{"CallPriority":{"Priorities":[
  {"targets":{"unitType":["platform","indoor"]},"priority":0,"timeout":60},
  {"targets":{"unitType":["VoIP"]},"priority":1,"timeout":60},
  {"targets":{"unitType":[]},"priority":2,"timeout":60}]}}
```

То есть панель сначала **60 секунд** звонит на монитор (indoor) и в платформу,
и только если не ответили — на VoIP, то есть в наш Asterisk. Приложение узнаёт
о звонке ровно в этот момент: в базе звонки длятся 62 и 68 секунд, потому что
запись создаётся тогда, когда панель уже переключилась на SIP.

**Чем это не лечится:** `PUT` этой настройки панель отвергает даже со своим же
содержимым (`400 badJsonContent`) — раздел только для чтения. Менять нужно в
веб-интерфейсе панели.

**Что нужно сделать (Дима, веб-интерфейс панели):**

- раздел «Интерком → Приоритет вызова» (Call Priority);
- либо добавить `VoIP` в запись приоритета 0, чтобы монитор и приложение
  звонили одновременно;
- либо уменьшить `timeout` приоритета 0 до 5–10 секунд — тогда монитор
  звонит коротко, и вызов сразу уходит в приложение.

Резервная копия исходной настройки сохранена на сервере:
`/root/panel-callpriority-backup.json`.

**Сделано параллельно (по остальным замечаниям):**

| Замечание | Что сделано |
|---|---|
| Видео слишком качественное | приложение переведено на дополнительный поток панели (канал 102: 640×480, 512 кбит/с), главный (1280×720, 2048 кбит/с) остался видеодомофону. Расход упал втрое: 343 КБ за 15 с вместо 1,1 МБ |
| После «Открыть» панель не сбрасывает вызов | миграция 020: `intercom_calls.ami_channel`; после открытия или отказа отправляем в Asterisk `Action: Hangup` — «положить трубку» |
| Защита от зависших звонков | перед созданием нового звонка закрываем записи в статусе `ringing` старше двух минут, иначе они блокируют новые по уникальному индексу |

### 1.33. Видео в окне звонка: плеер медиасервера и «тёплый» поток (06.11.2026)

**Проблема:** чёрный экран 5–10 с, затем неподвижный кадр, затем поток с
задержкой 10+ с.

**Причина:** `<video src=mp4>`. Браузер начинает показ с ближайшего ключевого
кадра и держит буфер; у панели ключевой кадр раз в ~4 с. Плюс сама RTSP-сессия
с панелью поднимается только в момент, когда появляется зритель (1–3 с).

**Что сделано:**

| Что | Как |
|---|---|
| Плеер | встроенный плеер go2rtc через iframe: `/go2rtc/stream.html?src=panel`, поток идёт по WebSocket (MSE) |
| Камера панели | `cameras.stream_url` = `/go2rtc/stream.html?src=panel` |
| «Тёплый» поток | служба `go2rtc-warm` (`scripts/go2rtc-warm.sh`) держит постоянного зрителя, поэтому сессия с панелью всегда открыта и первый кадр приходит почти сразу |
| Рамка | 4:3 (камера отдаёт 640×480), окно не прыгает при старте |

**Плата за «тёплый» поток:** постоянные ~512 кбит/с по туннелю. Отключается
одной командой: `systemctl disable --now go2rtc-warm`.

**Мелочь:** строка «Открыто» теперь исчезает через 4 секунды, а не висит до
перезагрузки. Таймер сбрасывается новым сообщением, на размонтировании
очищается.

### 1.34. Параллельный звонок: панель → наш сервер → приложение + монитор (06.11.2026)

**Задача.** Панель умеет только последовательный вызов (монитор 30 с, затем
VoIP) и не даёт объединить цели в одну группу — проверено Димой перебором,
минимум 30 секунд. Нужно, чтобы приложение звонило сразу, а монитор при этом
не терял вызов.

**Решение — перенести разветвление к нам:**

```
панель ──► Asterisk ──┬──► монитор (SIP-абонент 1..16)
                      └──► приложение (окно по событию AMI, сразу)
```

На панели достаточно оставить приоритет 0 = VoIP; кого звать дальше, решает
Asterisk.

| Что сделано | Где |
|---|---|
| План набора звонит в два места | `scripts/asterisk-parallel-ring.sh`, сейчас `Dial(PJSIP/${EXTEN}&PJSIP/1,30)` |
| Откат одной командой | `scripts/asterisk-parallel-ring.sh --off` |
| Учётка для монитора | `/root/monitor-sip-credentials.txt` (600 root): сервер, порт, логин `1`, пароль, номер комнаты |
| Абоненты 1..16 | уже заведены в `pjsip.conf` (auth1..auth16, alaw/ulaw) — монитору осталось зарегистрироваться |

**Проверено:** пробный вызов поднимает два плеча (`Dial(PJSIP/100&PJSIP/1,30)`,
плечо 100 активно), а событие в приложении создаётся сразу — до того, как
кто-либо ответил.

**Что осталось (только на железе):**

1. **Монитор** — вписать в его меню «Настройки → Сеть → SIP-сервер» данные из
   `/root/monitor-sip-credentials.txt`. Это единственное неизвестное: умеет ли
   `F-VI-3442IPWE1` регистрироваться на сторонний SIP-сервер. Веб-интерфейса у
   него нет, настройка только с экрана.
2. **Панель** — переставить приоритет 0 на `VoIP` (только наш сервер). Через
   API не получается: `PUT` с любым изменением порядка отвечает
   `400 badJsonContent`, даже при совпадающих таймаутах. Только веб-интерфейс.

**Риск, который проверится первым звонком:** звук на монитор через Asterisk
почти наверняка пойдёт (тот же G.711), а вот видео монитор может требовать
поток напрямую от панели. Если видео пропадёт — придётся либо оставить
последовательную схему с 30 секундами, либо ставить SIP-совместимый монитор
(BAS-IP, Akuvox) на боевом объекте.

### 5.1. Следствия решения по вопросу 1 (Вариант C)

**Статусная модель заявки упрощается:**

```
Новая → Принята → Назначен исполнитель → В работе
      → Ожидает материалов или доступа → Выполнена → Закрыта
                                                      ↑
                                        (исполнитель ставит сразу)
      Отклонена (в любой момент до «Выполнена»)
```

**Из MVP убираем:**
- `Подтверждение выполнения жителем` (пункт ТЗ 4.2);
- `Повторное открытие обращения` (пункт ТЗ 4.2) — **пока под вопросом**, см. ниже.

**Что НУЖНО учесть в UI (компенсация):**
1. После «Закрыта» житель **видит результат**: фото исполнителя, комментарий, время.
2. Обязательно — **комментарий исполнителя** при закрытии (нельзя закрыть без отметки о работе).
3. Кнопка **«Проблема не решена»** у жителя → создаёт **новую** заявку со ссылкой на исходную (связь `parent_ticket_id`). Это заменяет «повторное открытие» и даёт метрику повторных обращений — она нужна в аналитике.
4. В ЖК/доме — жалоба на качество → уведомление админу УК.

**Это сознательное упрощение MVP:** меньше кода, меньше конфликтов «кто прав», быстрее запуск. Повторное открытие с полноценным workflow (переразбор, апелляция) — v2, если пилот покажет потребность.

### 5.2. Следствия решения по вопросу 2 (Вариант A)

**Флоу регистрации жителя:**
1. Житель регистрируется (телефон, ФИО, e-mail — по минимуму).
2. Выбирает: УК → ЖК → дом → квартиру.
3. **Статус связи: `PENDING`** — до подтверждения видит только свой профиль, заявки не создаёт (или создаёт, но не видит чужих — см. ниже).
4. Админ УК видит список «Ожидают подтверждения» в своём кабинете.
5. Подтверждает → `CONFIRMED`. Отклоняет → `REJECTED` с причиной.

**Таблица `resident_bindings`** (не одна квартира на жителя):
- один житель может быть привязан к **нескольким** квартирам (владеет двумя) — это реальность;
- на одну квартиру — **несколько** жителей (собственник, супруг, арендатор);
- поля: `user_id`, `apartment_id`, `status`, `role_in_apartment` (собственник / арендатор / представитель), `confirmed_by`, `confirmed_at`.

**Что решает:** защита от чужих данных. Без подтверждения любой мог бы написать «я из кв. 42» и видеть её заявки.

**Вопрос к согласованию:** может ли житель создавать заявку **до** подтверждения? Я предлагаю **нет** — иначе теряется смысл подтверждения. Но диспетчеру можно регистрировать заявку «от имени жителя» — это закрывает срочные случаи (позвонил, приложение не установлено).

**РЕШЕНО (02.11.2026):** житель **НЕ может** создавать заявку до подтверждения привязки админом УК.
Обоснование: подтверждение теряет смысл, если неподтверждённый пользователь уже пишет заявки. Срочные случаи закрывает диспетчер — регистрирует обращение по телефону «от имени жителя» (`source = dispatcher_phone`).

### 5.4. Следствия для схемы БД и API

- В `tickets` обязателен `source` (`resident_app` | `dispatcher_phone` | `dispatcher_walkin`), чтобы отличать каналы.
- Проверка права «создать заявку» = есть `resident_bindings` со `status = confirmed` **и** `apartment_id` совпадает с заявкой.
- Для заявок, созданных диспетчером, `created_by` = сотрудник УК, а `contact_phone` обязателен (иначе не связаться).
- В UI жителя до подтверждения: главный экран показывает статус «Ожидает подтверждения», кнопка «Создать заявку» заблокирована с пояснением + телефон диспетчера УК.

## 8. Как продолжить работу на другой машине

|---|---|

| Серийный номер | DS-KD9633-E60020230524ENAB6832493 |
| Прошивка | V2.3.9, build 241016 |
| Сеть | `192.168.2.108`, порты 80 (ISAPI), 443, 8000 (SDK), 554 (RTSP) |
| Учётка интеграции | `admin` — **временно**, на стенде; пароль только в `.env` |
| Реле | 1 — `electricLock` (COM1), 2 — `disable` (COM2); `alarmOutNum=2` |

### 9.2. Как открывается (проверено руками)

Штатный ISAPI, ничего патчить не нужно:

```
PUT /ISAPI/AccessControl/RemoteControl/door/<N>
<?xml version="1.0" encoding="UTF-8"?>
<RemoteControlDoor><cmd>open</cmd></RemoteControlDoor>
```

Ответ при успехе:

```xml
<ResponseStatus>
  <statusCode>1</statusCode><statusString>OK</statusString>
  <subStatusCode>ok</subStatusCode>
</ResponseStatus>
```

Доступные команды (из `/ISAPI/AccessControl/RemoteControl/door/capabilities`):
`open`, `close`, `alwaysOpen`, `resume`. Используем только `open`:
`alwaysOpen` оставляет дверь открытой до `resume`.

Авторизация — HTTP **Digest** (`qop=auth`, MD5), два запроса: 401 с nonce →
запрос с хешем. Пароль не ходит в URL.

Чего у панели нет: `GET /ISAPI/AccessControl/RemoteControl/door/N` (статус
двери) отвечает 404, `/ISAPI/System/status` тоже. Устройство не сообщает,
сколько секунд держать замок — берём из `ACCESS_VENDOR_HOLD_SECONDS`.

### 9.7. Ловушки ISAPI, на которые уже наступили

1. **`alertStream` только по GET.** На POST панель отвечает
   `400 methodNotAllowed`. Тело части — **JSON**, хотя `Content-Type:
   multipart/mixed`.
2. **Одна сессия потока.** Пока предыдущее соединение не отпущено, следующий
   запрос получает `404` или `401` без `WWW-Authenticate`. Ждать ~30 с.
3. **Буфер событий.** При подключении панель вываливает всю историю (в нашем
   случае — с мая 2026). События надо фильтровать по `dateTime`.
4. **401 без `WWW-Authenticate`.** Если панель отвергла digest-хеш, она
   отвечает `401` **без** заголовка. Клиент обязан сбросить кэш nonce и
   сделать новое рукопожатие, иначе получает серию 401 и рискует блокировкой
   учётки. Исправлено в `isapi_client.py`, 12 запросов подряд — без ошибок.
5. **`psql` и кириллица.** Русский литерал в SQL из консоли Windows уходит
   в cp866 и сервер отвечает `invalid byte sequence for encoding "UTF8"`.
   Для UPDATE-ов использовать ASCII (`WHERE kind = 'wicket'`).
6. **`alertStream` и `httpHosts` — не синонимы.** Адрес в `httpHosts`
   сохранён, но панель по нему не стучится ни на открытие, ни на вызов, даже
   после сохранения в веб-интерфейсе.

### 1.40. «Файл не выбран» при выборе фото (06.11.2026)

**Симптом:** выбираешь три фото, а рядом с полем написано «Файл не выбран»;
кажется, что уйдут не те файлы, а после отправки прикрепляются все, что выбирал.

**Причина.** Это не ошибка загрузки, а поведение браузера: нативное
`<input type="file">` после выбора мы очищаем (`value = ''`), иначе повторный
выбор того же снимка не вызывает `change`. Браузер послушно рисует
«Файл не выбран», хотя файлы уже в состоянии, а счётчик рядом — правильный.
Путаница из двух сообщений, противоречащих друг другу.

**Что сделано:**

| Было | Стало |
|---|---|
| Нативное поле с «Файл не выбран» | Поле скрыто, вместо него кнопка «Приложить фото» |
| Счётчик «3 фото» | Список файлов по именам с крестиком у каждого |
| — | Подпись «выбрано N из 5» |
| Повторный выбор того же файла | Дубликат отсекается по имени, размеру и времени изменения |
| Список очищался после загрузки | Очищается **до**: повторное нажатие «Отправить» не отправит те же фото снова |

Компонент `PhotoPicker` один для трёх мест: создание заявки, комментарий,
форма закрытия. Заодно убрано обновление состояния в уборке эффекта превью —
ссылку blob освобождаем через замыкание эффекта.

**Проверено на проде:** в сборке есть «Приложить фото», «Приложить фотоотчёт»,
«выбрано»; строки «Файл не выбран» больше нет.

### 1.42. Открытия по гостевому коду не попадали в журнал (06.11.2026)

**Симптом:** гость открывает калитку кодом — в «Последних открытиях» у жителя

   («Строитель Пётр»), берётся из `apartment_members` по `memberId` из `detail`.
3. `memberId` кастуется в `uuid` только после проверки формата — иначе запрос

### 1.43. Приоритет вызова: параллельность в данных есть, запись закрыта (07.11.2026)

### 1.44. Прорыв: настройки панели пишутся через сессионный логин (07.11.2026)

**Что думали раньше:** `callPriority` и `deviceCommunication` — «только для
чтения», потому что `PUT` отвечал `400 badJsonContent`.

**Что оказалось:** в коде веб-интерфейса панели эти ресурсы помечены
`security1: ["regPassword"]`. Им нужен не Digest, а сессионный логин:
`sessionLogin/capabilities` → соль и challenge → пароль по формуле
`sha256(login+salt+pwd)`, затем `sha256(h+challenge)` и итерации →
`POST sessionLogin` → заголовок `SessionID`.

**Результат:** `PUT deviceCommunication` → `200 OK`, адрес платформы записан.
Появился инструмент `scripts/hikvision.py` (`get`, `put`, `set-manage`,
`session`, `backup`).

**И главное — окончательный ответ по параллельности.** Прогнали матрицу
через сессию:

| Комбинация | Ответ |
|---|---|
| `[indoor, VoIP]` | 400 badParameters |
| `[VoIP, indoor]` | 400 badParameters |
| `[indoor, VoIP, platform]` | 400 badParameters |
| `[indoor, VoIP]` с timeout 30 | 400 badParameters |
| `[platform, indoor]` | **200 OK** |
| `[indoor]`, затем `[VoIP]` | **200 OK** |

Прошивка **сознательно запрещает** монитор и VoIP в одном уровне. Значит
одновременного звонка «монитор + приложение» на этом железе не будет никогда —
ни настройкой, ни API. Вендорская параллель — только `platform` + `indoor`,
через платформу Hikvision.

**Состояние панели восстановлено** в исходную отладочную конфигурацию
(`VoIP` первым), адрес платформы снова `0.0.0.0`. Бэкапы в
`/srv/domkrug/backups/`.

**Что это даёт продукту:**
1. Конфигурацию панелей теперь можно менять программно — пригодится на пилоте.
2. Параллель с приложением возможна только если мы станем «платформой»:
   `manage = наш сервер` + протокол платформы (ISUP/EHome). На этой прошивке
   `Ehome`/`Integrate` отвечают `notSupport`, протокол надо выяснять по трафику.
3. Для домов с Hikvision — приложение первым (VoIP priority 0), монитор вторым,
   либо закупка панелей с нормальным параллельным SIP.
### 1.45. Параллельный вызов собран через callSignal (07.11.2026)

**Задача:** сделать одновременный звонок на монитор и в приложение любой ценой.

**Найден обход.** Панель запрещает `indoor`+`VoIP` в одном уровне приоритета,
но умеет поднимать вызов на монитор командой:

```
PUT /ISAPI/VideoIntercom/callSignal
{"CallSignal":{"cmdType":"request","target":{"unitType":"indoor","roomNumber":100}}}
→ 200 OK
```

Требования: сессионный логин (§1.44), `target` объектом, `unitType` только
`indoor`, `roomNumber` целым числом. `hangUp` работает без target.

**Схема:** панель звонит по VoIP (приоритет 0) → Asterisk видит INVITE →
скрипт поднимает вызов на монитор → оба звонят одновременно. После окончания
разговора скрипт отпускает вызов монитора.

**Сделано:**
- `scripts/ring-indoor.py` — вызов и сброс, до 8 попыток при `deviceBusy`;
- диалплан `[from-panel]`: триггер перед `Dial`, `hangup` после;
- `/etc/domkrug/panel.env` (`root:asterisk` 640) — Asterisk не root;
- конфиг панели оставлен как был: `VoIP` первым.

**Что осталось проверить кнопкой:** не отвечает ли панель `deviceBusy`, пока
сама звонит по VoIP. Если отвечает — монитор зазвонит только после разговора,
и схему надо будет переворачивать. Проверка возможна только живым нажатием.

### 1.51. Навигация после разделения: «вы не в том приложении» (07.11.2026)

**Симптом от владельца:** вход в приложение жителя с учёткой УК даёт 404.

**Причина:** после разделения клиентов вход по-прежнему уводил сотрудника на
`/inbox`, а этого раздела в приложении жителя больше нет. Человек попадал
на страницу 404 сразу после входа.

**Что сделано:**

| Ситуация | Было | Стало |
|---|---|---|
| Вход сотрудника в приложении жителя | редирект на `/inbox` → 404 | экран «Это приложение жителя» + «Открыть кабинет УК» + выход |
| Сотрудник зашёл по прямой ссылке внутрь | пустой раздел жителя | тот же экран |
| Житель открыл кабинет УК | текстовая заглушка | «Это кабинет управляющей компании» + «Открыть приложение жителя» + выход |

Общий компонент `packages/ui/src/WrongAppNotice.tsx` — дверь с двумя
створками, объяснение и кнопки; стили с запасными значениями, поэтому
выглядит одинаково в обоих приложениях.

**Проверка навигации целиком:**

- вход жителя: `/app/` → главная, разделы жителя, «Профиль»;
- вход УК: `/uk/` → инбокс; исполнителю — «Мои задания»;
- 404 в приложениях — общая страница с «На главную» и «Назад»;
- 404 на лендинге — для любого пути, кроме корня;
- старые адреса вроде `/inbox` на главном домене попадают на лендинг и дают 404.
### 1.52. Вход привязан к приложению (07.11.2026)

**Замечание владельца:** если в приложении жителя ввести логин и пароль УК,
система авторизовывала и сообщала «это другое приложение». По сути форма входа
подтверждала, что учётка существует и работает в УК — это утечка для перебора.

| Сценарий | Ответ |
|---|---|
| диспетчер → приложение жителя | 401 `INVALID_CREDENTIALS` |
| диспетчер → кабинет УК | 200, токен |
| житель → кабинет УК | 401 `INVALID_CREDENTIALS` |
| житель → приложение жителя | 200, токен |

### 1.56. Профиль сотрудника УК (07.11.2026)

**Задача:** сотрудник видел в шапке только имя и организацию. Он не знал,
какие права ему выдали, не мог сменить пароль, и не было места, куда придёт
второй фактор.

**Что сделано:**

| Файл | Что |
|---|---|
| `packages/shared/src/permissions.ts` | каталог 51 права: код → русское название, 8 групп |
| `packages/shared/src/roles.ts` | `ROLE_LABELS` и `roleLabel` — общие для обоих приложений |
| `apps/staff/src/pages/ProfilePage.tsx` | данные, организация, права, безопасность |
| `apps/staff/src/App.tsx` | маршрут `/profile` для всех сотрудников |
| `apps/staff/src/StaffLayout.tsx` | пункт «Профиль» в меню, имя в шапке — ссылка на профиль |

Экран состоит из четырёх блоков:

1. **Данные** — ФИО, телефон, e-mail; ФИО и почту можно изменить
   (`PATCH /auth/me`), телефон — нет: это идентификатор входа.
2. **Организация** — УК, должность, роли. Должность и роли назначает
   администратор, сотрудник их не правит.
3. **Права доступа** — только выданные права, сгруппированные по смыслу.
   Сырые коды вроде `ticket.view.all` сотруднику не показываются.
4. **Безопасность** — смена пароля и место под второй фактор.

**Почему без нового API:** `/auth/me` уже отдаёт `tenant.position`, `roles`
и `permissions`; `PATCH /auth/me` и `POST /auth/password/change` существуют
и покрыты тестами. Профиль — это представление, а не новый контракт.

**Смена пароля:** после успешного `POST /auth/password/change` клиент выходит.
Сервер и так закрывает все сеансы — оставаться «внутри» с мёртвым refresh
нечестно, поэтому правильный сценарий — войти заново.

**Проверено:**

- линт 0 ошибок (1 прежнее предупреждение в `IntercomCallOverlay`);
- 16 фронтенд-тестов (было 9): +4 каталог прав, +3 роли;
- 91 API-тест (было 90): добавлен тест «профиль сотрудника: /auth/me отдаёт
  организацию, должность и роли»;
- headless Chrome: вход диспетчером → `/profile`, все блоки на месте;
  скриншоты `screenshots/liviti-staff-profile.png` и `…-520.png`;
- `/auth/me` диспетчера: 26 прав, `tenant.position = «Диспетчер»`.

**Мелочи:**

- список прав свёрстан CSS `columns`, а не grid: grid оставлял пустые провалы
  под короткими группами;
- на мобильном full-page скриншоте нижнее меню попадает в середину — это
  артефакт захвата страницы целиком, а не вёрстки.

**Осталось:** сам второй фактор. В карточке «Безопасность» стоит честная
заглушка «Скоро» — следующим этапом туда встанут TOTP, QR-код и резервные
коды.

### 1.57. Второй фактор (TOTP) для диспетчеров и админов (07.11.2026)

**Задача:** у диспетчеров и администраторов доступ к ФИО, телефонам и
адресам сотен квартир. Одного пароля для таких учёток мало.

**Что сделано:**

| Файл | Что |
|---|---|
| `backend/migrations/021_two_factor.sql` | `users.totp_*`, таблица резервных кодов |
| `backend/src/lib/totp.ts` | TOTP на `node:crypto`, без внешних пакетов |
| `backend/src/modules/auth/two-factor-service.ts` | настройка, проверка, резервные коды |
| `backend/src/modules/auth/two-factor-routes.ts` | `/auth/2fa/*` |
| `backend/src/modules/auth/routes.ts` | вход требует код, если он включён |
| `apps/staff/src/pages/LoginPage.tsx` | поле кода появляется после пароля |
| `apps/staff/src/pages/ProfilePage.tsx` | подключение, резервные коды, отключение |

**Как работает:** секрет 20 байт в base32, 6 цифр, шаг 30 с, допуск ±1 шаг.
`setup` выдаёт секрет, но не включает вход; `enable` проверяет код и только
потом включает. Резервные коды (10 штук) хранятся хешами и одноразовые.
Отключение требует пароль **и** действующий код — иначе украденная сессия
снимала бы защиту. Подробности — `docs/2FA-TOTP.md`.

**Решения, которые стоит помнить:**

| Вопрос | Решение и почему |
|---|---|
| Внешняя библиотека | нет: алгоритм маленький, а зависимость тянет lock и риск на деплое; правильность проверена векторами RFC |
| Секрет в БД открытым текстом | это не пароль, но требования к базе те же; шифрование ключом приложения без KMS защищало бы только от дампа рядом с ключом |
| Принудительно блокировать вход без 2FA | нет: `required` — подсказка. Жёсткий флаг запер бы пилотные учётки, которые не успели настроиться |
| QR-код | пока нет: ключ вводится вручную или по `otpauth://`-ссылке; отдельный этап |
| Повтор кода в пределах 30 с | не отслеживается: риск ограничен HTTPS, коротким окном и лимитом входа |

**Проверено:**

- 32 юнит-теста (было 28): base32 и официальные векторы RFC 6238;
- 93 API-теста (было 91): обязательность для диспетчера и полный цикл
  «включение → вход по коду → резервный код → отключение»;
- 16 фронтенд-тестов, сборка трёх приложений, линт 0 ошибок;
- headless Chrome: пароль → поле кода → `/inbox`; экран подключения
  (секрет 32 символа, 10 кодов), профиль «Подключён».

**Грабли:**

1. `audit_log.action` проверяется регуляркой `^[a-z][a-z0-9_]*\.[a-z]...` —
   `auth.2fa_*` начинается с цифры после точки и падал с 500. Переименовали
   в `auth.two_factor_*`.
2. Префикс `/auth/2fa` + маршрут `/` даёт `/auth/2fa/`; чтобы не зависеть от
   завершающего слеша, маршруты объявлены как `/2fa`, `/2fa/setup` и т. д.

**Осталось:** QR-код, сброс второго фактора администратором УК, жёсткое
принуждение по роли и защита от повтора кода — отдельными этапами.

### 1.58. Wildcard `<slug>.liviti.ru` (07.11.2026)

**Задача:** у каждой УК свой адрес кабинета. Запись `*` в DNS уже была,
но Caddy не может выпустить сертификат на произвольный поддомен без
проверки — иначе любой получил бы валидный сертификат `что-угодно.liviti.ru`.

**Что сделано:**

| Файл | Что |
|---|---|
| `backend/src/modules/internal/routes.ts` | `GET /internal/tls/allow` — валидатор для Caddy |
| `backend/src/modules/public/routes.ts` | `GET /public/tenant?slug=` — имя УК для формы входа |
| `scripts/enable-wildcard.sh` | включает `on_demand_tls` и блок `*.liviti.ru`, проверяет сертификат |
| `apps/staff/src/pages/LoginPage.tsx` | на поддомене показывает «Кабинет <название УК>» |

**Как работает:** Caddy получает первый HTTPS-запрос на
`dom-service.liviti.ru`, спрашивает бэкенд, существует ли активная УК с
таким slug. `200` — выпускает отдельный сертификат на этот поддомен,
`403` — отказывает. Это не один wildcard-сертификат: у каждого поддомена
свой, поэтому не нужен DNS-01 и доступ к зоне. Все поддомены живут в одном
блоке `*.liviti.ru`, а `app`/`uk`/`www` разведены host-матчерами внутри
него.

**Грабли (важно):** первый вариант — отдельный блок `*.liviti.ru` рядом с
точными `app`/`uk`/`www` — адаптировался без ошибок, но в работе точные
хосты получали `TLS alert internal error`: политика wildcard выбиралась
раньше. Симптом: `uk` и `app` → `000`, `dom-service` → `200`. Откатили,
переделали на один wildcard-блок с host-матчерами; скрипт теперь проверяет
все адреса и сам откатывается при ошибке.

**Защита:** домен обязан заканчиваться на `.liviti.ru` (именно с точкой —
`liviti.ru` и `dom-service.liviti.ru.evil.com` не проходят), быть одним
уровнем, не входить в служебный список и совпадать с активной УК в базе.

**Проверено:** 95 API-тестов (было 93): разрешённые УК, несуществующий
slug, `app`/`uk`/`www`, чужой домен, суффикс-обман; публичный справочник.
Сборка, линт. На проде: `liviti.ru`, `app`, `uk` — 200, `www` — 301,
`dom-service` и `zhilkomfort` — 200; `doesnotexist-xyz.liviti.ru` получает
отказ TLS; форма входа на `dom-service.liviti.ru` показывает «Кабинет
ООО «Дом-Сервис»».

**Осталось:** при смене slug старый сертификат живёт до истечения;
автоматического удаления сертификатов нет.

### 1.59. Пароль демо-входов убран из публичного бандла (07.11.2026)

**Что нашли:** `scripts/deploy.sh` экспортировал `VITE_DEMO_LOGINS` с боевым
паролем. Экспорт переживал переход к сборке кабинета УК, поэтому пароль
попадал в **оба** публичных бандла и показывался на форме входа всем, кто
