## 5. Грабли, на которые уже наступали

1. **`npm ci` падает при новом воркспейсе** — lock не знает пакет. Нужно
   `npm install` и закоммитить `package-lock.json`. В деплое есть запасной
   `npm install`.
2. **Деплой исполняет старую версию скрипта** — `git pull` внутри скрипта не
   меняет уже загруженный файл. После правки `deploy.sh` запускать повторно.
3. **Chrome headless не даёт окно уже ~500px** — «мобильные» скриншоты врут;
   проверяйте на 520px или в реальном браузере.
4. **Тесты API зависят от состояния базы** — после нескольких прогонов
   сбрасывать базу (см. выше).
5. **Rate limit входа** — 10/мин; серия тестов подряд упирается в 429,
   помогает перезапуск API (счётчики в памяти).
6. **Панель Hikvision**: настройки читаются обычным Digest, а пишутся только
   через сессионный логин — инструмент `scripts/hikvision.py`.

### 0.2. Если «Permission denied (publickey)»

**Сначала узнать свой IP, потом смотреть лог — иначе увидите только ботов:**

```powershell
curl -s https://ifconfig.me/ip
```

```bash
journalctl -u ssh --since "-15 min" --no-pager | grep <ваш IP>
```

| Что в строке | Значение |
|---|---|
| `Accepted publickey for deploy` | доступ есть, проблема не в нём |
| `ROOT LOGIN REFUSED FROM …` | стучитесь как `root` — нужен `deploy` |
| `Connection reset … [preauth]` | ключ не подошёл |
| пусто | до сервера не доходят пакеты |

Проверить, что сервер вообще предлагает только ключи:

```bash
ssh -o PreferredAuthentications=none deploy@198.51.100.10
# → Permission denied (publickey) — это норма
```

### 0.3. Домашний агент: как вернуть себе доступ (2 минуты, без консоли)

Ключ домашней машины был стёрт 05.11 при настройке. Приватный ключ на месте,
вернуть нужно только публичную часть.

**Важно:** добавлять ключ следует **в панели Timeweb**, а не в консоли. На
сервере стоит переносчик (`liviti-sync-root-keys.sh`, cron раз в минуту):
всё, что вы добавляете в панели пользователю `root`, через минуту появляется
у `deploy`. Это сделано как раз потому, что `root` по SSH запрещён.

1. **Дома** взять публичный ключ:

   ```powershell
   type $env:USERPROFILE\.ssh\domkrug_pilot_ed25519.pub
   ```

   Если файла нет — `dir $env:USERPROFILE\.ssh\*.pub` или сгенерировать:
   `ssh-keygen -t ed25519 -f $env:USERPROFILE\.ssh\liviti_home`

2. **Панель Timeweb** → сервер `domkrug-pilot-01` → вкладка «Доступ» →
   «SSH-ключи» → «Загрузить новый ключ» → вставить строку → сохранить.

3. **Подождать до минуты** и проверить:

   ```powershell
   ssh deploy@198.51.100.10 hostname
   # pilot-api
   ```

Если через 2 минуты не пускает — ключ не доехал до панели; тогда аварийный путь
через консоль описан в `docs/SERVER-ACCESS.md`, раздел 3.

**Только `>>`, никогда `>`** — именно `>` затёр файл 05.11.

### Что понадобилось для Docker (сделано 03.11.2026)

1. **VT-x в BIOS** — включён владельцем.
2. **Компоненты Windows** — включены под администратором:

```powershell
Enable-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform -All -NoRestart
Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Windows-Subsystem-Linux -All -NoRestart
```

3. **Обновление WSL.** Встроенный в Windows 10 2004 `wsl.exe` не знает `--install`/`--update`.
   Лечится командой `wsl --update` из-под администратора — ставит WSL 3.0.1.
   Перезагрузка после этого не потребовалась.

Проверить окружение целиком:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\docker-preflight.ps1
```

### История: почему в compose нет MinIO

**MinIO перевёл свои образы с Docker Hub в архив** — `hub.docker.com/v2/repositories/minio/minio/`
отдаёт 404 (проверено 03.11.2026), а `quay.io/minio/minio` требует авторизации (401).
`bitnami/minio` существует, но без тегов.

Поэтому в `docker-compose.yml` вместо MinIO стоит **SeaweedFS** (активный проект с S3 API)
под профилем `storage`: он не стартует по умолчанию, потому что фото заявок ещё не реализованы.

```powershell
docker compose up -d                      # только PostgreSQL
docker compose --profile storage up -d    # + S3-хранилище, когда понадобится
```

Сервис хранилища **ещё не проверен в работе** — включится вместе с эндпоинтом `/attachments`.

**Пока работаем на нативном PostgreSQL.** Это не костыль: дома проект так и работал,
а `DATABASE_URL` в `.env` одинаковый для обоих вариантов.

Тесты на **Node + Vitest**, не на PowerShell. Это принципиально: раньше тесты

## 5. Важные технические заметки (ловушки, на которых уже спотыкались)

1. **База данных не переносится через Git.** На каждой машине она своя; наполняется
   через `npm run migrate` + `npm run db:seed`.
2. **Кириллица в путях убивает PostgreSQL на Windows.** См. раздел 0. Пути —
   только латиницей.
3. **`initdb` с русской локалью падает.** При создании кластера выставляйте
   `LC_ALL=en_US.UTF-8` — иначе `initdb` печатает вывод в cp1251 и падает на
   собственном сообщении. В `scripts\db-start.ps1` это уже сделано.
4. **`initdb` не может сменить права на каталог**, если сессия — Microsoft-аккаунт
   и каталог вне профиля пользователя. Поэтому кластер создаётся в ASCII-пути
   `C:\domkrug-pg`, а не в `C:\Program Files` или корне диска.
5. **`.env` не в репозитории** — он в `.gitignore`. Создаётся из `.env.example`.
6. **Windows PowerShell и кириллица:** файлы `.ps1` должны быть в UTF-8 **с BOM**,
   иначе 5.1 читает их как ANSI и падает на русских строках. Тело JSON-запросов
   отправлять байтами UTF-8, иначе кириллица искажается.
7. **`npm` в PowerShell блокируется ExecutionPolicy** (`npm.ps1`). Из агента
   вызывайте `C:\Program Files\nodejs\npm.cmd`, а не `npm`.
8. **Лимит частоты запросов в development отключён.** Иначе трёх наборов тестов
   (100 запросов с одного IP) не хватало: общий счётчик 10 входов в минуту
   блокировал четвёртый вход, и `api-tickets` падал. В production лимиты прежние
   (`allowList` действует только вне production).
9. **Kaspersky ругается на сам DeepSeek Harness** (`PDM:Exploit.Win32.Generic`
   на `DeepSeek Harness.exe`), не на проект. Если начнутся внезапные
   `Permission denied` / `spawn EPERM` — проверьте его отчёты и добавьте
   исключение на папку установки Harness.

## 6. Правила работы (из ТЗ v1.1)

1. Не удалять работающий код без согласования.
2. Не менять архитектуру без обоснования.
3. Небольшие независимые задачи, тесты после каждого этапа.
4. Не создавать фиктивные интеграции.
5. Не выдавать демонстрационные функции за реальные.
6. Не подключать платные сервисы и не арендовать сервер без согласования.
7. Секреты — только в DPAPI (`C:\Users\<user>\.dsh\secrets\`), не в репозитории.
8. После этапа — отчёт: что сделано, файлы, что работает, ошибки, тесты, что дальше.
9. Обновлять `PROGRESS.md` после каждого этапа — это мост между машинами.

10. **Коммит — это запись в журнале, а не «wip».** Первая строка — до 72 знаков,
    повелительное наклонение, без точки. Тело — 3–6 строк: зачем сделано, что
    именно изменилось, чем проверено, что осталось. `git log` читают как
    историю проекта, поэтому «fix», «upd», «правки» — запрещены.

    Образец:

    ```
    Стенд домофонии: Hikvision DS-KD9633-E6 открывает калитку по ISAPI

    Провайдер hikvision: Digest-авторизация и PUT /ISAPI/AccessControl/
    RemoteControl/door/<N>. Номер реле берётся из access_points.provider_ref,
    параметры устройства — из ACCESS_VENDOR_* в .env.

    Проверено: открытие из интерфейса — HTTP 200 за 813 мс, запись в
    access_events; 15 unit + 72 API-теста; check-encoding 210 файлов.
    Осталось: второе реле (COM2 в disable), учётка интеграции вместо admin.
    ```

11. **Комментарий в коде объясняет «почему», а не «что».** `i++` понятно и без
    комментария; а вот почему реле берётся из точки, а не из конфига, почему
    digest считается двумя запросами, почему `psql` нельзя передать русский
    литерал — это и есть ценность комментария. Ловушки, на которые уже
    наступали, описывать прямо у кода, а не только в `PROGRESS.md`.

12. **Журнал ведётся в двух местах: `PROGRESS.md` и Pull Request.** После
    этапа — раздел в `PROGRESS.md` (что сделано, как проверено, что открыто)
    и PR с тем же содержанием. Ветка не вливается в `main` без этого: у
    следующей машины не должно быть шанса не узнать, что произошло.
