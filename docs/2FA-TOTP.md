# Второй фактор (TOTP) для сотрудников УК

**Дата:** 07.11.2026
**Статус:** работает, включён для всех ролей; принудительно — пока нет
**Код:** `backend/src/lib/totp.ts`, `backend/src/modules/auth/two-factor-*.ts`,
`apps/staff/src/pages/ProfilePage.tsx`

---

## 1. Зачем

Диспетчер и администратор УК видят ФИО, телефоны и адреса сотен квартир.
Одного пароля для такой учётки мало: пароли утекают при фишинге и
переиспользуются на других сайтах. Второй фактор превращает украденный
пароль в бесполезный — без кода из телефона войти нельзя.

Требование из плана: «2FA для диспетчеров и админов» — у них доступ к данным
сотен квартир.

---

## 2. Как это выглядит для сотрудника

1. Открыть **Профиль → Безопасность → Второй фактор**.
2. Нажать «Подключить» — покажется ключ (base32, 32 символа) и ссылка
   `otpauth://` для приложения-аутентификатора.
3. Добавить ключ в Google Authenticator / Authy / 1Password вручную
   или открыть ссылку на телефоне.
4. Ввести 6-значный код — только после этого второй фактор включается.
5. Сохранить 10 резервных кодов: они показываются один раз.
6. При следующем входе после пароля появится поле «Код из приложения».

Отключение — там же: нужен пароль **и** действующий код (обычный или
резервный). Одной сессии мало, иначе украденный токен снимал бы защиту.

---

## 3. Как это устроено

| Часть | Решение |
|---|---|
| Алгоритм | TOTP по RFC 6238: HMAC-SHA1, 6 цифр, шаг 30 с, допуск ±1 шаг |
| Секрет | 20 байт (160 бит) в base32 — рекомендуемый размер RFC 4226 |
| Библиотека | нет: `node:crypto` + свой base32; проверено векторами RFC |
| Хранение | `users.totp_secret` (base32), `users.totp_enabled`, `users.totp_enabled_at` |
| Резервные коды | `totp_backup_codes`, sha256, одноразовые, 10 штук |
| Миграция | `backend/migrations/021_two_factor.sql` |

Допуск ±1 шаг нужен из-за расхождения часов телефона и сервера. Без него
человек с правильным кодом получал бы «неверный код» и не понимал почему.

**Почему секрет в базе открытым текстом.** Это не пароль: восстановить
пароль по нему нельзя, но без него не сгенерировать коды. База уже хранит
`password_hash`, поэтому требования к её защите те же. Шифрование секрета
ключом приложения добавим, когда появится KMS или ключ вне репозитория;
иначе ключ лежал бы рядом с базой и защищал только от дампа.

## 4. Поток настройки

```
POST /auth/2fa/setup   → { secret, otpauthUrl }   секрет записан, totp_enabled=false
POST /auth/2fa/enable  → { backupCodes[] }        код проверен, totp_enabled=true
```

`setup` можно вызывать повторно: старый неиспользованный секрет заменяется.
Пока код не подтверждён, вход по второму фактору **не требуется** — иначе
человек, начавший настройку и закрывший вкладку, запер бы себя.

---

## 5. Поток входа

```
POST /auth/login { identifier, password, audience }
  ├─ второй фактор выключен        → 200, сессия
  ├─ включён, кода нет             → 401 TOTP_REQUIRED
  ├─ включён, неверный код         → 401 INVALID_TOTP
  └─ включён, верный код/резервный → 200, сессия
```

`TOTP_REQUIRED` возвращается только после верного пароля и проверки
приложения — до этого ответ такой же, как на неверный пароль. Клиент по
коду ошибки показывает поле ввода, а не «неверный пароль».

Повторное использование кода в пределах 30-секундного окна сейчас не
отслеживается. Риск ограничен: код живёт 30 секунд, вход идёт по HTTPS,
а частота попыток ограничена общим лимитом входа. Если понадобится —
добавим `totp_last_step`.

## 6. Ограничения и что дальше

| Ограничение | Почему / когда исправим |
|---|---|
| Нет QR-кода | Ключ вводится вручную или по `otpauth://`-ссылке. QR добавим отдельным этапом — не хотим тянуть зависимость ради одной картинки |
| Нет принудительного включения | `required` — подсказка, вход без 2FA не блокируется. Иначе при включении флага все неприготовленные учётки заперлись бы; включим, когда все настроятся |
| Нет сброса администратором УК | Потерянный телефон + потерянные коды = правка в БД. Отдельный сценарий «сбросить второму фактору» — следующий этап |
| Нет «моих устройств» | Сессии не показываются; 2FA от этого не зависит |

## 7. Проверка

**Юнит-тесты** (`backend/tests/unit/totp.test.ts`): base32 туда-обратно и
официальные векторы RFC 6238 для SHA1 (6 цифр).

**API-тесты** (`backend/tests/api/two-factor.test.ts`):

- диспетчеру `/auth/2fa` отдаёт `required: true`, `enabled: false`;
- полный цикл на свежем пользователе: setup → неверный код → включение →
  вход без кода (`TOTP_REQUIRED`) → неверный код → вход по TOTP →
  вход по резервному коду → повторное использование отклонено →
  неверный пароль при отключении → отключение → вход по паролю.

**Живой браузер (headless Chrome):**

- вход диспетчером: пароль → появляется поле «Код из приложения» →
  код → `/inbox`;
- профиль показывает «Подключён» и «Резервных кодов осталось: 10»;
- экран подключения: секрет 32 символа, 10 резервных кодов, отключение 204.

## 8. Если потерян телефон

1. Ввести один из резервных кодов в поле «Код из приложения» при входе.
2. После входа — отключить второй фактор и настроить заново.

Если потеряны и коды — пока только правка в базе:

```sql
UPDATE users SET totp_secret = NULL, totp_enabled = false, totp_enabled_at = NULL
 WHERE phone = '+7...';
DELETE FROM totp_backup_codes WHERE user_id = (SELECT id FROM users WHERE phone = '+7...');
```

Отдельный административный сценарий сброса — в плане.
