# Журнал решений «ДомКруг»

Хронология спорных решений: **контекст → варианты → выбрали → почему**.
Нужен, чтобы через полгода не переоткрывать вопросы и не спорить с самим собой.

## 02.11.2026 — Отказ от аудита существующего проекта

**Контекст:** ТЗ v1.0, Этап 1 требует «изучить существующий проект DomKrug».
**Факт:** проекта нет, работа с нуля.
**Решение:** Этап 1 переопределён в проектирование. Аудит не проводится.
**Почему:** аудировать нечего; вместо него — проектный пакет, который реально нужен.

## 02.11.2026 — PWA вместо нативных приложений

**Контекст:** ТЗ рекомендует Flutter для iOS/Android.
**Варианты:** Flutter сразу / PWA в MVP + нативные в v2 / только веб.
**Решение:** PWA в MVP.
**Почему:** один разработчик + ИИ; три клиента — тройная трудоёмкость и три релизных процесса. Публикация в App Store требует аккаунтов, проверок и времени.
**Цена решения:** на iOS push-уведомления ограничены. Принято сознательно, задокументировано в ТЗ v1.1 п. 5.3.

## 02.11.2026 — Fastify вместо NestJS

**Контекст:** ТЗ рекомендует NestJS.
**Решение:** Node.js + TypeScript + Fastify.
**Почему:** NestJS добавляет DI-контейнер, декораторы и «магию», которая затрудняет отладку одиночке. Fastify даёт явные обработчики и меньше неявных связей.
**Риск:** меньше «из коробки» — структуру модулей задаём папками сами.

## 02.11.2026 — Vite + React вместо Next.js

**Контекст:** ТЗ рекомендует Next.js.
**Решение:** SPA на Vite + React.
**Почему:** SEO не нужен (CRM и кабинет жителя), SSR добавляет отдельный сервер и деплой. Меньше узлов — меньше поломок.

## 02.11.2026 — Мультиарендность через `tenant_id`, не через схемы

**Варианты:** отдельная схема PostgreSQL на УК / общая схема с `tenant_id` / отдельная БД на УК.
**Решение:** общая схема + `tenant_id` на всех бизнес-таблицах.
**Почему:** миграции и бэкапы — одна операция вместо N; при 2–3 УК разделение схем даёт только сложность.
**Ограничение:** при тысячах УК понадобится шардирование. Это далёкая перспектива, не повод усложнять сейчас.

## 02.11.2026 — Заявку закрывает исполнитель, без подтверждения жителем

**ТЗ v1.0 предполагает:** исполнитель «Выполнена» → житель «Закрыта», плюс повторное открытие.
**Решение (выбор владельца):** исполнитель закрывает сразу.
**Почему:** меньше кода и меньше споров «кто прав». Быстрее запуск пилота.
**Компенсация:** житель видит результат (фото, комментарий); кнопка «Проблема не решена» создаёт новую заявку со ссылкой на исходную (`parent_ticket_id`) — это и замена повторному открытию, и метрика повторных обращений.
**Что потеряли:** возможность оспорить закрытие в рамках той же заявки. Вернуть — v2, если пилот покажет потребность.

## 02.11.2026 — Житель привязывается к квартире сам, с подтверждением УК

**Варианты:** приглашение от УК / самостоятельная регистрация + подтверждение / без подтверждения.
**Решение (выбор владельца):** сам регистрируется, ждёт подтверждения админа УК.
**Почему:** без подтверждения любой мог бы заявить «я из кв. 42» и видеть её заявки.
**Следствие:** житель **не может создавать заявки** до подтверждения. Срочные случаи — диспетчер регистрирует по телефону (`source = dispatcher_phone`).

## 02.11.2026 — `resident_bindings` как М:М, а не «одна квартира на жителя»

**Контекст:** наивная модель — поле `apartment_id` в `users`.
**Почему отвергнуто:** один человек владеет двумя квартирами; на одну квартиру — собственник, супруг, арендатор. Поле в `users` ломается на первом же таком случае.
**Решение:** отдельная таблица связи со статусом и ролью в квартире.

## 02.11.2026 — `users` без `tenant_id`

**Контекст:** интуитивно «пользователь принадлежит УК».
**Почему отвергнуто:** сантехник УК живёт в доме, который она же обслуживает. Один человек — житель одной УК и сотрудник другой.
**Решение:** принадлежность выражается через `staff`, `user_roles.tenant_id`, `resident_bindings`.

## 02.11.2026 — `platform_admin` не видит данные УК

## 02.11.2026 — Хостинг: Timeweb Cloud, Новосибирск, 1 vCPU / 6 ГБ / 15 ГБ

**Варианты:** Timeweb / Selectel / выделенный сервер Рег.ру / сервер в офисе.
**Решение:** Timeweb Cloud, Новосибирск, 3 380 ₽/мес.
**Почему:** сервер в РФ (152-ФЗ), дешевле Москвы на ~28%, ближе к пилотным УК. Отдельный выделенный сервер Рег.ру отвергнут: старый Xeon 2012 г. и SATA-диски при цене выше. Сервер в офисе отвергнут: нет отказоустойчивости, ПДн УК зависят от офисного электричества.
**Ограничение:** диск 15 ГБ мал — фото заявок идут в S3 (~79 ₽/мес).

## 02.11.2026 — Git как единственный мост между двумя машинами

**Контекст:** работа ведётся с домашней и рабочей машины, контекст чата не переносится.

## 02.11.2026 — Гибридная схема окружения: нативный PostgreSQL + Docker для деплоя

**Контекст:** домашний ноутбук — 6,9 ГБ RAM (8 ГБ минус iGPU), свободно 16 ГБ на C: и 7,7 ГБ на D:.
Docker Desktop занял бы 6–9 ГБ диска и 2–3 ГБ RAM, а вместе с Node, браузером и DSH
память кончается — система уходит в своп, сборки замедляются.

**Варианты:**
- Docker Desktop везде — единообразие, но машина не тянет;
- Нативный PostgreSQL везде — легко, но расходится с прод-окружением;
- **Гибрид:** нативный PostgreSQL на слабой машине, Docker на рабочей (700 ГБ диска, 8+ ГБ RAM) и на сервере.

**Решение:** гибрид.
- домашняя машина: портативный PostgreSQL 16 (`.local/pgsql`, `.local/pgdata`), без установки в систему и без прав администратора;
- рабочая машина: Docker Desktop, `docker compose up -d`;
- сервер: Docker.

**Почему:** Postgres в обоих случаях один и тот же (16.9), SQL и миграции идентичны —
расходится только способ запуска. Экономия: ~200 МБ RAM и ~350 МБ диска вместо 3 ГБ и 9 ГБ.

**Что учесть:** файлы (S3/MinIO) в разработке на домашней машине будут на локальном диске
через адаптер хранилища; MinIO появится только на Docker-машине. Интерфейс хранилища
абстрагирован, чтобы переключение было настройкой, а не правкой кода.

**Риск:** две разные схемы запуска надо проверять отдельно. Поэтому: перед пилотом
обязателен прогон `docker compose` на рабочей машине.

## 02.11.2026 — Портативный PostgreSQL вместо установщика

**Контекст:** на домашней машине нужна база, но установщик EDB требует прав администратора,
создаёт службу Windows и оставляет следы в системе.

**Решение:** портативная сборка (zip 300 МБ) в `.local/`, инициализация `initdb`,
запуск `postgres.exe` отдельным процессом через `scripts/db-start.ps1`.

**Почему:** не требует прав администратора, ничего не устанавливается в систему,
`docker-compose`-аналог на минималках. Данные лежат в проекте — удаляется папкой.

**Ограничение:** не стартует автоматически с Windows. Запуск — `scripts/db-start.ps1`,
остановка — `scripts/db-stop.ps1`. Для ежедневной работы это приемлемо.

**Грабли, найденные на практике:** `pg_ctl start` держит stdout-поток, поэтому запуск
через захват вывода в PowerShell зависает. Запускать надо через `Start-Process`
с редиректом в файл — так и сделано в скриптах.

## 03.11.2026 — Фронтенд: Vite + React без дополнительных слоёв

**Контекст:** нужно 17 экранов для трёх ролей; один разработчик + ИИ.

**Решение:** Vite + React + TypeScript, `react-router-dom`, CSS-переменные без
UI-библиотеки, свой тонкий клиент на `fetch`. Без Redux, React Query, MUI/AntD,
Storybook и SSR.

**Почему:** глобального состояния почти нет (пользователь и токен) — хватает
React Context. Единственный нетривиальный сценарий (обновление токена на 401) проще
написать в 40 строк, чем настраивать библиотеку. Компонентная библиотека притащила бы
свой дизайн, который пришлось бы переопределять под `DESIGN.md`.

**Когда пересмотреть:** если экранов станет больше 40 или появится потребность
в кешировании списков между переходами — тогда React Query.

## 03.11.2026 — Прокси Vite вместо настройки CORS для cookie

**Контекст:** refresh-токен живёт в httpOnly cookie с `SameSite=Strict`, фронт и
бэк в dev на разных портах.

**Решение:** dev-сервер Vite проксирует `/api` на `localhost:3000`; в коде —
относительные пути.

**Почему:** при прокси запросы идут с того же origin, cookie работает без послаблений
CORS. Настраивать `Access-Control-Allow-Credentials` и `SameSite=None` ради разработки
означало бы ослабить защиту, которая нужна в проде.

**В production:** фронт и API на одном домене (или поддомене с корректным CORS),
прокси — на уровне nginx/Caddy.

## 03.11.2026 — MinIO через Docker отложен: образ удалён с Docker Hub

**Контекст:** `docker-compose.yml` ссылается на `minio/minio:RELEASE.2025-04-22T22-12-26Z`.
При первом `docker compose up` выяснилось: **MinIO удалил свои образы с Docker Hub**
(`pull access denied`), а `quay.io/minio/minio` требует авторизации.

**Варианты:**
1. Перейти на неофициальное зеркало (`bitnami/minio`, `alpine/minio`) — работает, но это образ третьей стороны, и за ним никто не следит.
2. Запускать MinIO официальным бинарником без Docker — как сделано с PostgreSQL.
3. Отложить до момента, когда S3 реально понадобится.

**Решение:** вариант 3 сейчас; выбор между 1 и 2 — перед шагом «фото в заявке».

**Почему:** эндпоинта `/attachments` ещё нет (см. `FRONTEND-PLAN.md`, п. 8.2),
поэтому хранилище файлов сейчас не нужно вообще. Подключать неофициальный образ
«на всякий случай» — значит принять риск, у которого нет отдачи.

**Это объективный факт, а не наша поломка:** та же проблема у Apache Flink,
Carbynestack и objectfs. Владельцу стоит знать: при переезде на прод MinIO
придётся тянуть откуда-то ещё или разворачивать на своём сервере (Timeweb Cloud S3 — вариант из `PROGRESS.md` п. 2.3).

## 03.11.2026 — SeaweedFS вместо MinIO (замена решения выше)

**Контекст:** решение «отложить» оставляло в репозитории нерабочий сервис:
`docker compose up -d` — команда из README — падала на скачивании образа.
Документация не должна учить команде, которая не работает.

**Проверено 03.11.2026:** `hub.docker.com/v2/repositories/minio/minio/` → **404**;
`quay.io/minio/minio` → **401** (нужна авторизация); `bitnami/minio` → **0 тегов**
(не вариант, как в первом решении). Доступны: `chrislusf/seaweedfs` (тег 3.80),
`dxflrs/garage` (v2.5.0).

**Решение:** SeaweedFS 3.80 в `docker-compose.yml` под профилем `storage`.
`docker compose up -d` поднимает только PostgreSQL; хранилище включается
`docker compose --profile storage up -d`.

**Почему профиль, а не всегда:** фото заявок ещё не реализованы — незачем
поднимать лишний контейнер на каждом запуске. И почему не удалить совсем:
когда появится `/attachments`, не придётся вспоминать, чем заменить MinIO.

**Статус:** сервис **не проверен в работе**. Флаги `server -dir=/data -s3`
и порт 8333 нужно подтвердить при реализации загрузки файлов.
Альтернатива при проблемах — Garage: тоже активен, конфигурируется TOML-файлом.

## 03.11.2026 — В разработке лимиты увеличиваются, а не отключаются

**Контекст:** тесты идут с одного IP и упирались в лимит входа 10/мин.
Первым решением было `allowList: () => true` — отключить лимиты в development целиком.

**Почему отвергнуто:**
1. Отключённый механизм не выполняется в разработке вообще — ошибка в нём
   обнаружится только в production.
2. `allowList` по IP обходится заголовком `X-Forwarded-For`, если сервер
   случайно окажется доступен по сети (а `trustProxy` включён).

**Решение:** `scaledLimit(max)` в `backend/src/lib/limits.ts` — в development
лимит умножается на 50. Механизм работает и проверяется, тесты не упираются.

**Заодно:** CORS в development ограничен `http://localhost:5173` вместо
`origin: true` (открытый CORS с credentials — риск); при старте в
непроизводственном режиме в лог пишется предупреждение.

**Остаточный риск:** `NODE_ENV` по умолчанию `development`. Если на сервере
его забыть, включится dev-режим: лимиты ×50, CORS только localhost (фронт
не откроется) и заглушка `JWT_SECRET`, если переменная не задана. Перед
пилотом нужен чек-лист деплоя: `NODE_ENV=production`, `JWT_SECRET`, `APP_URL`.

## 04.11.2026 — Процесс заявки: кнопки по роли и назначению

**Контекст.** Владелец описал процесс так, как он его видит, и проверил
интерфейс на телефоне в Chrome. Текущая логика расходилась с описанием:
кнопок было больше, чем нужно, и часть из них не имела смысла для роли.

**Как описал владелец:**

- житель создаёт заявку, может комментировать и **удалить** её;
- диспетчер принимает, назначает исполнителя, отклоняет. **После назначения
  у него остаются только две кнопки: переназначить и отклонить**;
- если диспетчер назначил сам себя — он может взять в работу и закрыть;
- сантехник и электрик — только «Взять в работу» и «Закрыть»;
- администратор — всё на любой стадии.

**Решение.** Кнопки вычисляются из роли, назначения и статуса, а не из
одного списка прав. Лишние **скрываются**, а не блокируются: на телефоне
список из недоступных кнопок читается хуже, чем короткий список.

| Роль | Видит |
|---|---|
| Житель | комментарий, «Удалить заявку», «Проблема не решена» (после закрытия) |
| Диспетчер (не назначен) | «Назначить/Переназначить», «Отклонить» |
| Диспетчер (назначен) | «Взять в работу», «Закрыть», «Переназначить», «Отклонить» |
| Исполнитель (назначен) | «Взять в работу», «Закрыть» |
| Админ УК | всё на любой стадии |

**Что убрано из интерфейса:** «Принять заявку» (назначение само по себе
означает принятие) и «Ожидает материалов» (в описанном процессе этого шага
нет). Статус `waiting` остался в базе — для заявок, которые уже в нём.

**Удаление жителем** реализовано как мягкое (`deleted_at`), с записью в
аудит. Чужую заявку удалить нельзя: сервер отвечает 404 так же, как на
несуществующую — чтобы нельзя было перебором узнать, какие заявки есть.

## 04.11.2026 — Норматив SLA убран с карточки

**Контекст.** В карточке заявки показывался норматив в часах по категории.

## 04.11.2026 — Главная жителя как витрина сервисов

**Контекст.** Главная показывала только заявки. Продукт задуман шире:
доступ на территорию, шлагбаум, камеры, счётчики, оплата ЖКУ, лифты,
подсветка, экстренные вызовы.

**Решение.** Сетка из десяти сервисов. Работает пока один — «Заявки»;

## 04.11.2026 — Поиск квартиры свёрнут в кнопку «Добавить недвижимость»

**Контекст.** На экране «Квартира» под списком привязок всегда была открыта

привязка не сработала.

**Решение.** Если привязки есть, форма скрыта и раскрывается кнопкой

тяжёлой — меняется в одном месте.

состояние хранит только выбор пользователя. Вариант через `useEffect`
с `setState` линтер отклонил справедливо: это лишний рендер и лишняя точка
рассинхронизации.

## 04.11.2026 — ЕСИА (Госуслуги) откладываем

**Контекст.** Владелец спросил, можно ли сделать подтверждение личности через
Госуслуги и нужно ли это.

**Что выяснили по [официальному порядку подключения](https://info.gosuslugi.ru/articles/Как_подключиться_к_ЕСИА/):**

1. Подтверждённая УЗ руководителя + КЭП + регистрация организации в ЕСИА + проверка ФНС.
2. **Предусловие — регистрация ИС в СМЭВ** с той же мнемоникой (отдельный контур и договор).
3. Заявка на тестовую среду: нормативно-правовые акты как основание, scope,
   сертификат ключа ЭП ИС, лицензии и договоры.
4. Заявка на продуктивную среду.

Реальный срок — **3–6 месяцев** с интегратором: СКЗИ, СМЭВ, аттестация ИС.
Отдельная сложность — правовое основание доступа к ЕСИА для коммерческого сервиса.

**Решение: откладываем.** На пилоте личность подтверждает УК при подтверждении
привязки — этого достаточно, объём ручной работы при 2–3 УК минимален.

**Когда вернёмся:**

- **голосование собственников (ОСС)** — там идентификация обязательна;
- автоподтверждение привязки при росте числа УК;
- платежи, где нужна достоверная идентификация плательщика для чека.

**Дешёвая альтернатива сейчас:** необязательное поле СНИЛС в профиле +
сверка с реестром собственников УК. Совпало — привязка подтверждается
автоматически. Без СМЭВ и месяцев ожидания. Поле добавляем заранее, чтобы
не менять схему потом.

## 04.11.2026 — Житель с несколькими квартирами в разных УК

## 04.11.2026 — Выгрузку недвижимости из ЕСИА и ФНС не делаем

**Контекст.** Вопрос: можно ли получить объекты недвижимости человека из
Госуслуг или nalog.ru при подтверждении личности.

**Ответ: нет.** Разбор источников:

| Источник | Что можно | Чего нельзя |
|---|---|---|
| ЕСИА | ФИО, СНИЛС, ИНН, документы | **Не отдаёт объекты недвижимости** — это идентификация, не имущество |
| nalog.ru (ФНС) | Налогоплательщик видит свои объекты в ЛК | API для третьих лиц отсутствует |
| ЕГРН (Росреестр) | Выписки, API для аккредитованных | Платно, по аккредитации; обычной ИТ-компании не дадут |
| ГИС ЖКХ | Сведения о помещениях и собственниках | Доступ через УК как поставщика информации |

**Что используем вместо этого:**

1. Подтверждение привязки управляющей компанией — основной путь, уже работает.
2. ЕСИА → СНИЛС → сверка с реестром УК (когда ЕСИА появится).
3. Загрузка выписки ЕГРН или фото квитанции жителем — распознаём адрес и ЛС.
4. Выгрузка из ГИС ЖКХ через УК, если она готова.

**Решение:** своей интеграции с ЕГРН и ФНС не делаем. Источник истины о
собственности — управляющая компания.

## 04.11.2026 — СНИЛС храним в открытом виде, с проверкой контрольной суммы

**Контекст.** СНИЛС нужен, чтобы УК могла сверить жителя с реестром
собственников и подтвердить привязку без ручной проверки.

**Варианты:**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Хранить хеш | Безопаснее при утечке | Нельзя показать человеку его номер и объяснить, что не совпало |
| Хранить в открытом виде | Работает сверка, понятные ошибки | При утечке базы номер становится известен |

**Решение: открытый вид.** СНИЛС — не пароль: он не даёт доступа к аккаунту,
но позволяет сопоставить человека с реестром. Хеш сделал бы сверку
невозможной, а «не совпало» без деталей — бесполезным сообщением.

**Что компенсирует риск:** доступ к полю только владельцу и (в будущем)
сотрудникам УК по праву; поле необязательное; в интерфейсе показывается
в формате `123-456-789 01`, в базе — только цифры.

**Контрольная сумма обязательна.** Без неё опечатка создаёт несуществующий
номер, сверка не срабатывает, и мы ищем ошибку не там, где она есть.
Зарезервированный диапазон (меньше 001-001-998) тоже отклоняется.

## 04.11.2026 — СКУД: сначала контракт провайдера, потом железо

**Контекст.** Владелец просит подготовиться к интеграции СКУД: открытие ворот,
дверей, просмотр домофонии.

**Что выяснили про рынок:**

| Вендор | API | Примечание |
|---|---|---|
| BAS-IP | SIP, HTTP, **Mobile SDK** | активен в РФ, SDK для встраивания видеодомофона в своё приложение |
| Akuvox | HTTP API, SIP, облако | распространён в новостройках |
| 2N | полный HTTP API, SIP, RTSP | эталон по документации, но поставки в РФ ограничены |
| Hikvision / Dahua | ISAPI / RPC, RTSP | массово, но серый импорт |
| Vizit, Tantos, Slinex, Commax | часто без API | стоят в большинстве домов, интеграция только через замену панели или шлюз |

**Решение: сначала модель данных и контракт, потом вендор.**

Причины:
1. Вендоры отличаются транспортом, авторизацией и форматом ответа. Если
   начать с конкретного, вторая интеграция потребует переделки экранов.
2. Без железа можно проверить права, журнал и изоляцию — на mock-провайдере.
3. Выбор вендора зависит от того, что **уже стоит** у УК, а не от наших
   предпочтений.

**Реализовано:** таблицы `access_points`, `access_grants`, `access_events`;
интерфейс `AccessProvider`; `MockAccessProvider`; маршруты жителя
(`/resident/access/points`, `/points/:id/open`, `/events`); экран «Доступ»
и быстрые кнопки на главной.

**Ключевые правила:**
- доступ выдаётся **квартире**, а не человеку: право выводится из
  подтверждённой привязки, при отзыве привязки исчезает само;
- чужая точка неотличима от несуществующей (404 в обоих случаях);
- отказы тоже пишутся в журнал;
- 5 открытий в минуту на человека — защита от «зажатой» кнопки;
- mock-провайдер нельзя включать на реальном доме: он сообщает «открыто»,
  но дверь не открывается. Это написано и в коде, и на экране.

## 04.11.2026 — Виджет на домашнем экране: две кнопки доступа

**Идея владельца.** Когда доступ заработает через приложение, вынести на
домашний экран телефона виджет с двумя большими кнопками: «Открыть подъезд»
и «Открыть шлагбаум». Чтобы не искать разделы в приложении.

**Техническое ограничение:** PWA **не умеет** добавлять виджеты на домашний
экран. Это возможно только в нативном приложении:

- Android — App Widget (RemoteViews / Glance);
- iOS — WidgetKit (начиная с iOS 14), кнопки-действия требуют App Intents.

**Путь:** обернуть текущую PWA в нативное приложение (Capacitor или
React Native), затем сделать виджет, который вызывает наши эндпоинты
`/resident/access/points/:id/open` с `source: 'widget'`.

Поле `source` в журнале уже поддерживает значение `widget` — когда виджет
появится, в журнале будет видно, что дверь открыли с домашнего экрана.

**Сейчас:** на главной есть блок из двух больших кнопок (подъезд и шлагбаум)
для текущей квартиры — это ближайший аналог виджета без нативного кода.

## 04.11.2026 — Видео: скелет без медиасервера, с честным демо-режимом

**Контекст.** Владелец просит видеонаблюдение с доступом только к своим
камерам и картинку с вызывной панели при звонке в домофон.

**Что важно технически:**

1. Браузер **не воспроизводит RTSP** — стандарт де-факто у камер. Нужен либо
   HLS, либо WebRTC через медиасервер (go2rtc, MediaMTX, Janus). Прямая
   вставка потока в `<video>` не работает.
2. Видео — персональные данные. Ссылка на поток должна быть короткоживущей
   и подписанной, иначе её перешлют и камеру будет смотреть кто угодно.
3. Доступ к камере — отдельное право, не то же самое, что право открыть
   дверь. Смешивать нельзя: однажды видео утечёт туда, где разрешено только
   открытие.

**Решение для скелета:**

- Таблицы `cameras` (тип потока `demo|hls|webrtc|sip`, адрес, провайдер)
  и `camera_grants` — доступ выдаётся квартире, как и точки доступа.
- `GET /resident/video/cameras` — только свои камеры, без дублей.
- `GET /resident/video/cameras/:id/stream` — короткоживущий токен (5 минут).
  В демо-режиме возвращается `demo: true` и `url: null`: честнее показать
  заглушку, чем битую ссылку.
- `intercom_calls` — журнал звонков: кто, в какую квартиру, чем закончилось.
  Живёт 60 секунд, потом помечается пропущенным.
- Звонок создаётся через `POST /resident/video/intercom/demo-call` — имитация
  нажатия кнопки. В реальности это будет вебхук от вызывной панели, заменится
  одна функция.
- Ответ на звонок открывает дверь **через тот же провайдер доступа**, что и
  обычная кнопка: права и журнал единые.

**Про реальный эфир в интерфейсе:** в демо-режиме вместо видео — заглушка
с бегущей полосой, часами и подписью «ДЕМО». Чёрный прямоугольник выглядит
как поломка, а притворяться, что это камера, — хуже поломки.

**Опрос вместо WebSocket.** Звонок подтягивается раз в 5 секунд. Для скелета
достаточно, но для реального домофона задержка великовата: когда появятся
настоящие звонки — SSE или WebSocket, отдельным решением.

## 04.11.2026 — Калитка и подъезд: один сценарий звонка

**Вопрос владельца.** Когда звонят в калитку или подъезд, должна быть картинка
с камеры вызывной панели.

**Решение.** Сценарий один для любого типа точки: событие звонка привязано
к `access_point_id`, а камера — отдельная сущность (`cameras`), связанная
с точкой. Поэтому:

- подъездный домофон, калитка, шлагбаум с камерой — одинаковый поток:
  звонок → картинка → «открыть» / «отклонить»;
- если у точки нет камеры (простой шлагбаум), звонок всё равно возможен,
  просто без картинки;
- если у точки несколько камер (вызывная панель + обзорная), звонок берёт
  камеру типа `call_panel`.

Так мы не заводим отдельные сущности «домофон» и «калитка»: разница только
в типе точки доступа.

## 04.11.2026 — Счётчики: жёсткие правила ввода

**Контекст.** Показания — данные, из которых считают деньги. Ошибка в них
превращается в неверную квитанцию и спор с бухгалтерией УК.

**Решение — три правила на сервере, а не в интерфейсе:**

1. **Один прибор — одно показание за период.** Уникальный индекс
   `(meter_id, period)`; повторная передача обновляет значение, а не создаёт
   вторую запись. Иначе в квитанции окажется два разных числа.
2. **Показание не может быть меньше предыдущего.** Счётчик не крутится назад.
   Если прибор заменён — это отдельный процесс с участием УК, а не «исправление»
   в приложении.
3. **Период — текущий месяц.** За будущее показаний не существует, за
   позапрошлое уже сформирована квитанция.

Житель может исправить своё показание за текущий месяц (ошибся при вводе) —
это разрешено. Понизить относительно прошлого месяца — нет.

## 04.11.2026 — Лифты: статус меняет УК, не житель

**Контекст.** Кнопка «сообщить о неисправности» не должна сама переводить
лифт в статус «неисправен»: один житель может нажать её у исправного лифта,
и остальные увидят ложную тревогу.

**Решение:**

- житель создаёт **событие** `fault` с описанием — оно уходит в УК;
- статус лифта меняет сотрудник УК после проверки;
- если лифт уже в статусе `fault`, вызов из приложения запрещён (403).

**Зачем вообще «вызвать лифт» в приложении,** если у лифта есть кнопка:
для гостя или курьера, когда жителя нет дома. Это второстепенный сценарий,
поэтому вызов просто пишется в журнал, без сложной логики.

## 04.11.2026 — Экстренные вызовы: не изображаем то, чего нет

**Контекст.** Владелец просил блок экстренных сообщений и вызовов.

**Главное ограничение:** экстренные службы (112, скорая, полиция, пожарные)
**не принимают вызовы через сторонние приложения**. Изобразить «вызов
отправлен в скорую» технически можно, но это опасно: человек отложит телефон
и будет ждать.

**Решение:**

- для экстренных служб показываем **номер телефона** и фиксируем намерение
  в журнале — но не пишем «вызов принят»;
- для **аварийной службы УК** вызов уходит по-настоящему: это наш партнёр;
- журнал обязателен: по нему разбирают, кто и когда вызывал;
- отмена возможна, пока вызов не принят;
- кулдаун 5 минут — защита от случайного двойного нажатия и от «зажатой»
  кнопки.

**Сообщения УК** — отдельная сущность: могут быть по всей УК или по
конкретному дому, имеют уровень важности (`info`, `warning`, `critical`)
и срок действия. Житель видит только сообщения своих домов.

## 04.11.2026 — Экстренные службы: только звонок, без «вызова из приложения»

**Уточнение к решению выше.** Владелец попросил, чтобы кнопка 112 набирала
номер на телефоне.

**Решение:** экстренные службы (112, 101, 102, 103, 104) — это ссылки
`tel:`, а не запросы на сервер. Нажатие открывает набор номера, человеку
остаётся нажать «Вызов». Сервер при этом ничего не записывает: звонок идёт
мимо нас, и делать вид, что мы его «зарегистрировали», нельзя.

**Аварийная служба УК остаётся в приложении** — это наша служба, вызов
уходит диспетчеру с адресом и квартирой, и он сохраняется в журнале.

## 04.11.2026 — Меню жителя: четыре пункта и плитки

**Контекст.** Владелец заметил: на десктопе «Профиль» не влезает в меню,
на телефоне не влезают ни верхнее, ни нижнее.

**Решение:** в навигации жителя остаются **Главная, Заявки, Доступ,
Квартира** (+ Профиль). Остальные разделы — Камеры, Оплата, Счётчики,
Лифты, Экстренно — открываются плитками с главной.

Почему так, а не «прокрутка»: пункт меню, до которого нужно докручивать,
на телефоне не находят. Плитки на главной видны все сразу, и это ровно то,
ради чего главная делалась витриной.

## 04.11.2026 — Члены квартиры вместо «семьи»

**Контекст.** Владелец спросил: как женой и детьми пользоваться приложением,
если они не собственники; и как дать временный доступ строителю.

**Почему не «семья»:** строитель — не семья, ребёнок — не гость, арендатор —
не родственник. Если завести сущность «семья», через месяц она обрастёт
исключениями. Поэтому сущность — **член квартиры** с набором прав.

**Модель:** `apartment_members` (телефон, пресет, scopes, статус, срок,
кто пригласил). Владелец — подтверждённая привязка УК, в таблицу не входит:
у него все права по умолчанию, дублировать их в двух местах опасно.

**Права — флаги, а не роль:**

| Право | Что открывает |
|---|---|
| `access.open` | двери, калитки, шлагбаум |
| `video.view` | камеры и звонок с вызывной панели |
| `meters.submit` | передача показаний |
| `tickets.create` | создание заявок |
| `finance.view` | начисления (пока только у владельца) |
| `members.manage` | приглашения и отзыв |

**Пресеты:** семья (двери + видео + показания + заявки), ребёнок (только
двери), арендатор (как семья, со сроком), рабочий и гость (только двери,
срок обязателен).

**Ключевое техническое решение — представление `apartment_rights`.**
Раньше каждый модуль сам джойнил `resident_bindings`, и любой подтверждённый
житель получал всё: и видео, и показания, и двери. С членами так нельзя.
Теперь права собраны в одном представлении, а модули проверяют `can_open`,
`can_video`, `can_meters`, `can_tickets`. Иначе через полгода в одном модуле
проверка была бы, а в другом — забыта.

**Инвайт по номеру телефона.** Приглашение живёт в таблице по телефону.
Человек ставит приложение, регистрируется этим номером — при входе
приглашение подхватывается автоматически (`claimInvites`). Никаких кодов
и ссылок: номер уже есть.

**Срок обязателен для рабочего и гостя** — иначе через полгода в подъезд
войдёт человек с просроченным доступом, о котором владелец забыл.

**Отзыв действует сразу:** строка помечается `revoked`, представление
перестаёт отдавать права, двери закрываются. Заявки, созданные человеком,
остаются у квартиры — они часть истории дома.

## 04.11.2026 — Доступ по коду: без регистрации и персональных данных

**Контекст.** Владелец возразил против регистрации для чужих людей:
ребёнок не может сам дать согласие на обработку ПДн, а строителю незачем
сдавать паспорт, чтобы открыть дверь.

**Решение:** собственник создаёт **код доступа** в своём кабинете и передаёт
его человеку любым способом. Человек вводит код на экране входа и получает
урезанный экран: адрес, кнопки открытия, срок действия. Ни телефона, ни
ФИО, ни пароля, ни согласия на обработку ПДн — их просто нет.

**Почему это безопасно:**

- код — 8 символов из алфавита без похожих (`0/O`, `1/I/L` путают при
  диктовке), 32^8 ≈ 1,1⋅10^12 вариантов;
- в базе хранится **bcrypt-хеш**, сам код не хранится и не восстанавливается;
- вход по коду ограничен 10 попытками в минуту с адреса;
- ответ на неверный, истёкший и отозванный код одинаковый — нельзя узнать,
  какие коды существуют;
- права читаются из записи членства **при каждом запросе**, поэтому отзыв
  и истечение срока действуют немедленно, а не после истечения токена;
- гостевой токен имеет тип `guest`: `/auth/me`, `/resident/*` отвечают 401 —
  в обычные разделы попасть нельзя.

**Ответственность.** Владелец, выдав код, отвечает за того, кому он его дал.
Система не знает о нём ничего, кроме метки («Строитель Пётр») и срока —
это данные владельца о его госте, а не персональные данные гостя.

**Два способа доступа остаются:**

| Способ | Кому | Что даёт |
|---|---|---|
| Код | строитель, курьер, гость, ребёнок | двери и адрес, без истории |
| Телефон | жена, взрослые члены семьи | аккаунт с заявками и историей |

Код — способ по умолчанию: он не требует от человека ничего.

## 04.11.2026 — Метка доступа — внутренняя, гостю не показывается

**Контекст.** Владелец заметил: если подписать доступ «Балбес», человек
увидит это на своём экране.

**Решение:** поле «Для кого» — это **заметка владельца**, а не имя гостя.
Она видна только в списке доступа у владельца. Гостю отдаём заголовок
«Гостевой доступ» и адрес.

Проверяется на уровне API: `/guest/login` и `/guest/me` не содержат `label`
вообще, поэтому даже если интерфейс захочет его показать — показывать нечего.

## 04.11.2026 — Код доступа можно посмотреть и отправить

**Раньше:** код показывался один раз, в базе лежал только bcrypt-хеш.

**Почему изменили:** владелец вправе видеть ключ, который сам выдал —
код нужно продиктовать, отправить в мессенджер или повторить через день.
Терять его из-за однократного показа неправильно.

**Как:** хеш остаётся для проверки, рядом лежит **шифрованная копия**
(AES-256-GCM, ключ выводится из секрета приложения). Дамп базы без ключа
приложения коды не раскрывает. Код отдаётся только владельцу квартиры
(`members.manage`), гостю — никогда.

**Отправка:** кнопка «Отправить» вызывает системное «Поделиться» телефона
(WhatsApp, Telegram, SMS). В браузере без поддержки — копирует текст в буфер.

## 04.11.2026 — Телефон в приглашении нормализуется

**Ошибка:** владелец вводил «+7 923 240-15-20», а пользователь в базе
хранится как «+79232401520». Поиск не находил человека, приглашение
оставалось в статусе «ждёт входа» и не включалось никогда.

**Решение:** телефон приводится к виду `+7XXXXXXXXXX` при приглашении,
при поиске пользователя и при подхвате приглашения. Для старых записей
сравнение идёт по цифрам без форматирования — иначе уже выданные
приглашения остались бы сломанными.

## 04.11.2026 — Решение владельца: семья — по телефону, код — для разовых

**Выбор сделан владельцем (вариант A).** Разделение простое:

| Кому | Как | Что получает |
|---|---|---|
| Жена, взрослые члены семьи | **по телефону** (аккаунт) | двери, видео, показания, заявки, история |
| Ребёнок, рабочий, гость, курьер | **по коду** | только двери и шлагбаум |

**Почему не «код для всех»:** код анонимный — у него нет истории заявок,
нет «мои показания за прошлый месяц», нет профиля с контактами. Дать жене
код значило бы дать двери без всего остального.

**Что поправили в интерфейсе, чтобы это было видно:**

- в режиме «По коду» предлагаются только Ребёнок, Рабочий, Гость;
- в подсказке режима — «нужны видео, показания и заявки? Пригласите
  по телефону» со ссылкой, которая переключает режим и ставит «Член семьи»;
- переключение режимов само выставляет подходящий пресет, чтобы не было
  «Член семьи, а доступ только к двери».

**Проверено на проде:** приглашение «+7 900 000-09-04» (с пробелами и
дефисами) → `activated=true`, права `access.open, video.view, meters.submit,
tickets.create`; человек видит квартиру, 3 камеры, 3 счётчика и может
подать заявку.

## 04.11.2026 — Своя квартира и квартира по доступу различаются явно

**Контекст.** Человек может быть собственником одной квартиры и одновременно
иметь доступ к квартире жены. В переключателе обе выглядели одинаково,
и было непонятно, почему в одной есть начисления, а в другой нет.

**Решение:** переключатель подписывает квартиры «— моя» и «— по доступу»,
а на главной у чужой квартиры видна плашка «Доступ предоставил(а) … ·
эта квартира не ваша». Имя берётся из `invited_by`, поэтому видно, кто
именно дал доступ.

**Оплата — только для своей квартиры.** Проверка `finance.view` стоит
в самом экране, а не только в меню: в квартиру по доступу раздел не
открывается даже по прямой ссылке. Деньги — дело собственника; доступ
даёт двери и видео, но не лицевой счёт.

**Начисления переехали в «Оплату».** В профиле они дублировали раздел
и мешали: профиль про человека, оплата про деньги.
