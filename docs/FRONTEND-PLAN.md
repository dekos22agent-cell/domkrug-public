## 0. С чего начать завтра (первые 30 минут)

```powershell
# 1. Поднять окружение
docker compose up -d
cd backend; npm install; npm run migrate; npm run db:seed
npm run dev            # оставить в отдельном окне

# 2. Проверить, что API живой
#    http://localhost:3000/health/ready  →  {"status":"ok","checks":{"database":true}}

# 3. Создать фронтенд
cd ..
npm create vite@latest frontend -- --template react-ts
cd frontend
npm install
npm install react-router-dom
npm run dev            # http://localhost:5173
```

**Первая проверка:** страница Vite открывается, `fetch('/api/v1/health')` через прокси
возвращает `{"status":"ok"}`.

## 1. Стек (решено, не менять без причины)

| Что | Выбор | Почему |
|---|---|---|
| Сборка | **Vite** | Быстрый dev-сервер, минимум конфигурации |
| Язык | **TypeScript** | Типы API и ошибок ловят опечатки до запуска |
| UI | **React 18** | Стандарт, много примеров |
| Роутинг | **react-router-dom v7** | Вложенные маршруты по ролям |
| Стили | **CSS-переменные + модули** | Дизайн-система задана токенами в `DESIGN.md`; Tailwind не нужен на 17 экранах |
| Состояние | **React Context** (auth) + локальное | Глобального состояния мало: пользователь и токен |
| Запросы | **свой тонкий клиент на fetch** | Нужен один нетривиальный сценарий — refresh на 401; библиотека тут добавляет больше, чем экономит |
| Тесты | **Vitest** для утилит | Сквозные сценарии проверяются вручную и API-тестами |

**Чего НЕ делаем в MVP:** Redux, React Query, компонентные библиотеки (MUI/AntD),
SSR, Storybook. Всё это — когда появится реальная потребность.

## 3. Клиент API — самое важное место

Одна нетривиальная часть: **access-токен живёт 15 минут**, а refresh — в httpOnly cookie.
Клиент должен незаметно обновлять токен и повторять запрос.

```ts
// lib/api.ts — логика в двух словах
// 1. access-токен храним В ПАМЯТИ (не localStorage: XSS)
// 2. при 401 один раз пробуем POST /auth/refresh (credentials: 'include')
// 3. если refresh успешен — повторяем исходный запрос
// 4. если нет — разлогиниваем и ведём на /login
```

**Правила:**
- `credentials: 'include'` обязательно: без него cookie не отправляется.
- Одновременные 401 не должны вызывать несколько refresh — ставим общий промис
  («refresh в полёте»), остальные запросы ждут его результат.
- Ошибки API приходят в формате `{error:{code,message,details,requestId}}` —
  показываем `message`, а `requestId` выводим в консоль для разбора.

## 4. Порядок экранов и критерии готовности

### Шаг 1. Каркас + вход

- `LoginPage`: телефон или e-mail, пароль, кнопка «Войти».
- После входа — переход по роли: житель → `/`, диспетчер/админ → `/inbox`,
  исполнитель → `/my`.
- Ошибка неверного пароля показывается текстом, не алертом.

**Готово, когда:** вход под `+79000000001` / `Demo1234!` открывает инбокс,
под `+79000000101` — главную жителя.

### Шаг 2. Главная жителя

- Адрес и УК, статус привязки.
- Кнопка «Создать заявку».
- Последние 2–3 заявки с бейджами статусов.
- Если привязка не подтверждена — вместо кнопки блок с объяснением и телефоном УК.

**Готово, когда:** под Волковым (`+79000000105`, привязка pending) видно
«Ожидает подтверждения», кнопка недоступна.

### Шаг 3. Создание заявки

- Категория — сетка кнопок (12 штук, аварийные помечены).
- Срочность, описание, телефон, фото (пока без загрузки — отложить).
- После создания — переход на карточку заявки с номером.

**Готово, когда:** заявка создаётся и появляется в инбоксе диспетчера.

### Шаг 4. Инбокс диспетчера

- Список с фильтрами: статус, просрочка, аварийные.
- Просроченные выделены, аварийные — красная полоса.
- Клик открывает карточку.

**Готово, когда:** видно 10 демо-заявок, фильтр «просроченные» показывает одну.

### Шаг 5. Карточка заявки (диспетчер)

- Все данные, история, комментарии (включая служебные).
- Действия: принять, назначить (выбор из `/staff`), отклонить с причиной.

**Готово, когда:** назначение исполнителя меняет статус на «Назначен исполнитель».

### Шаг 6. Кабинет исполнителя

- Список назначенных, кнопки: в работу, ожидает материалов (с комментарием),
  закрыть (с описанием работ).

**Готово, когда:** исполнитель закрывает заявку, житель видит результат.

### Шаг 7. Привязка квартиры

- Поиск по адресу → выбор квартиры → заявка на привязку → статус «ожидает».
- У диспетчера — очередь подтверждений.

### Шаг 8. Адаптив и PWA

- Мобильная вёрстка (375px), нижняя навигация у жителя.
- `manifest.webmanifest`, иконки, `theme-color`.

## 5. Технические детали, которые сэкономят время

### Прокси в dev (обход CORS)

```ts
// vite.config.ts
export default defineConfig({
  server: {
    port: 5173,
    proxy: {
      '/api': { target: 'http://localhost:3000', changeOrigin: true },
    },
  },
});
```

Тогда в коде — относительные пути `/api/v1/...`, и cookie работает как same-origin.
**Без прокси** придётся настраивать CORS с credentials — лишняя возня.

### Токен в памяти и перезагрузка страницы

После F5 access-токен теряется, но refresh-cookie остаётся. Поэтому при старте
приложение делает `POST /auth/refresh`: если успешно — сразу восстанавливает сессию,
если нет — показывает вход. Это нормальный сценарий, не ошибка.

### Статусы: цвет и текст всегда вместе

По `DESIGN.md` статус обозначается цветом **и** подписью. Часть пользователей
не различает оттенки — только цвет недопустим.

### Числа из API

`count(*)` в PostgreSQL отдаётся строкой. Сервисы уже приводят к числу, но если
где-то встретится `"12"` вместо `12` — это причина, а не баг фронтенда.

## 6. Что делать, если API ругается

| Код | Что значит | Что делать |
|---|---|---|
| 401 `UNAUTHORIZED` | Токен истёк или подделан | Один refresh, потом выход |
| 403 `FORBIDDEN` | Нет права у роли | Показать «Недостаточно прав», не прятать кнопку молча |
| 403 `BINDING_NOT_CONFIRMED` | Житель без подтверждения | Ведём на экран привязки |
| 404 | Объекта нет **или он чужой УК** | Показать «Не найдено» |
| 409 `INVALID_STATUS_TRANSITION` | Недопустимый переход | Обновить карточку и показать актуальный статус |
| 422 `CANNOT_CLOSE_WITHOUT_RESOLUTION` | Пустое описание работ | Подсветить поле |
| 429 `RATE_LIMITED` | Слишком часто | «Попробуйте через минуту» |

**Нельзя:** показывать пользователю сырой JSON ошибки или `requestId` вместо
человеческого текста.

## 7. Проверка перед показом УК

1. Вход под каждой из ролей работает.
2. Сквозной сценарий: заявка → инбокс → назначение → закрытие → житель видит результат.
3. Две УК: диспетчер второй не видит заявок первой.
4. На телефоне (375px) ничего не разъезжается.
5. Пустые состояния: «Заявок пока нет» с подсказкой, а не пустой экран.

## 9. Чего не делать сейчас

- Не вводить состояние-менеджер «на будущее».

- Не подключать аналитику, Sentry, i18n.
- Не полировать анимации, пока не пройден сквозной сценарий.
