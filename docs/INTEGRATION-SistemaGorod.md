# Интеграция с Системой «Город» (Алтайский край)

**Дата разбора:** 04.11.2026
**Источники:** три документа от ЕРЦ (изучены локально, в репозиторий не копируются):
протокол информационного взаимодействия v3.11 от 09.07.2025, правила работы
Системы «Город» с 01.01.2026, разъяснения по оплате с QR-кодом.

---

## 1. Что это за система

ООО «Единый расчётный центр» (ЕРЦ) — оператор региональной платёжной системы
Алтайского края с 2003 года. По их данным, к системе подключены 99% организаций
ЖКХ края. Есть личный кабинет и мобильные приложения для жителей.

Для нас это важно: пилот в Барнауле, и начисления наших УК, скорее всего, уже
ведутся в этой системе.

---

## 2. Что реально даёт протокол v3.11

Протокол реализуется **двумя интерфейсами**:

| Интерфейс | Технология | Назначение |
|---|---|---|
| Создание и проведение платежей | **SOAP 1.2** + WS-Security 1.0 | Поиск абонента, форма, корзина, оплата, статусы, чеки |
| Выполнение отчётов | **REST** + OAuth (password grant, Bearer) | Отчёты, загрузка платёжных поручений |

Кодировка UTF-8, закрытые каналы связи, до 50 одновременных запросов.

### Функции SOAP-API

| Функция | Что делает |
|---|---|
| `formCalc` | Шаги 1–5: поиск, форма, пересчёт |
| `getCart` | Корзина платежей |
| `invoicePay` | Шаг 6: проведение платежа |
| `getStatus` | Статус платежа |
| `stornoPay` | Сторнирование (только текущий операционный день) |
| `getGisGmpInfo` | Данные для ГИС ГМП (УИН, КБК, ОКТМО, реквизиты) |
| `getCheque` | Печатная форма чека: позиции, НДС, ИНН агента и поставщика |

### Последовательность оплаты

1. **Шаг 1** — поиск услуг: `find_account_val` (лицевой счёт) либо адрес
   (`find_address_city_val`, `find_fias_street_val`, дом, квартира).
   Ответ: `session_id` + список услуг.
2. **Шаг 2** — календарь периодов. Ответ: адрес, `calendar`, `address_id`.
3. **Шаг 3** — форма оплаты. **Поля и их типы приходят в ответе** — то есть
   форму нужно рендерить динамически.
4. **Шаг 4** — пересчёт: `paysum` (включая комиссию с абонента), `commission`,
   `need_identification`, `is_preferential` (льготная комиссия ЖКХ).
5. **Шаг 5** — сохранение в корзину: `unp` — номер платежа, строки чека,
   `email_phone` для фискализации.
6. **Шаг 6** — `invoicePay(unp, paysum)`.

### Жизненный цикл платежа

| Срок | Состояние |
|---|---|
| до 1 часа | Активен, можно провести |
| 1 час — 8 суток | Может быть удалён, проведение невозможно |
| после 8 суток | Удаляется автоматически |

Операционный день — по Барнаулу (GMT+7). Сторно возможно только в тот же
операционный день и может быть запрещено поставщиком услуги.

### Статусы платежа (`getStatus`)

`NOT_FOUND` · `SAVED` · `DELETED` · `AUTH` (проведён) · `STORNED`

## 3. Роли по правилам системы

| Субъект | Кто это |
|---|---|
| **ЦЕНТР** | ООО «ЕРЦ» — организатор системы |
| **ОРГАНИЗАЦИЯ** | Банк либо **платёжный агент по 103-ФЗ** либо АО «Почта России» — принимает платежи |
| **КЛИЕНТ** | Поставщик услуг — УК, ресурсоснабжающая организация |
| **РАСЧЁТНАЯ ОРГАНИЗАЦИЯ** | Посредник, работающий по договору с поставщиками услуг |
| **АДМИНИСТРАТОР ПЛАТЕЖЕЙ** | Расчёты от своего имени с получателями |

**АРМ** (автоматизированное рабочее место) регистрируется ЦЕНТРОМ; технические
требования к каналам и оборудованию устанавливает ЦЕНТР. **ТАРИФЫ** — отдельный
документ с размерами вознаграждений участников, доступен участникам по
защищённому каналу.

## 4. QR-код с квитанции

Протокол поддерживает приём по QR, оформленному по **ГОСТ 56042-2014**:

1. Из QR извлекается `persAcc` — номер лицевого счёта → передаётся в
   `find_account_val` (шаг 1).
2. Из ответа показываем список услуг, выбранную передаём на шаг 2.
3. `paymPeriod` из QR → выбор периода на шаге 3; если реквизита нет — передаём
   признак оплаты текущей задолженности.

То есть **сканирование QR с квитанции — это штатный сценарий**, а не обходной путь.

## 5. Что это значит для нас

### Хорошие новости

- Спецификация полная: можно проектировать и писать код **до** получения доступа.
- Фискализация и ГИС ГМП — на их стороне (`getCheque`, `getGisGmpInfo`).
- Своя биллинговая система не нужна: начисления приходят из Системы «Город».
- Комиссия, льготы, несколько услуг в одной корзине — уже предусмотрены.

### Плохие новости

- **Протокол написан для стороны «Банк/платёжная система».** Прямо сказано:
  «Интерфейс для взаимодействия с пользователем реализует Банк, при этом Банк
  обязуется реализовать протокол в полном объёме». Доступ — по закрытым каналам,
  аутентификация WS-Security логин/пароль.
- Статус участия нужно получить: договор присоединения + регистрация АРМ.
  Реалистичные варианты для нас: стать **ОРГАНИЗАЦИЕЙ как платёжный агент**
  (103-ФЗ) либо работать через **банк-ОРГАНИЗАЦИЮ**, который уже подключён.
- **Динамическая форма.** Ответ шага 3 содержит поля с типами, и протокол
  требует показывать «только те поля, которые были указаны в ответе». Это
  конфликтует с нашим дизайном: придётся либо рендерить их форму, либо
  ограничиться сценарием «оплата по лицевому счёту» с предзаполненными полями.

## 6. Оценка работ

| Работа | Срок |
|---|---|
| SOAP-клиент + WS-Security, тестовый контур | 3–4 дня |
| Стейт-машина шагов 1–5, рендер динамической формы | 1,5–2 недели |
| Корзина, `invoicePay`, статусы, чек | 1 неделя |
| REST-отчёты (OAuth, реестры) + сверка | 1 неделя |
| Тестирование, обработка ошибок, идемпотентность | 1 неделя |
| **Итого** | **4–6 недель** |

Плюс время на договор и закрытый канал — это вне нашего контроля.

## 7. Вопросы, которые нужно задать ЕРЦ

1. Может ли ОРГАНИЗАЦИЕЙ быть не только банк, но и платёжный агент (103-ФЗ)?
2. Есть ли тестовый контур (`localhost` в примерах намекает, что да)?
3. Кто организует закрытый канал (VPN) и что для этого нужно?
4. Можно ли получить ТАРИФЫ и договор присоединения для оценки?
5. Обязателен ли полный протокол или допустим сокращённый сценарий
   (только ЖКУ, лицевой счёт из QR)?
6. Как передаётся реестр начислений поставщику — только через АРМ или есть выгрузка?

---

## 8. Рекомендуемый порядок действий

1. **Сейчас, без договора:** кнопка «Оплатить» с переходом в Систему «Город»
   (deep link). Два дня работы, ноль рисков, раздел «Оплата» оживает.
2. **Параллельно:** запрос в ЕРЦ по списку вопросов из раздела 7.
3. **Если доступ дадут:** писать SOAP-клиент против **мока по протоколу**
   (спецификация позволяет), затем переключить на их адрес.
4. **Если не дадут:** свой приём платежей через ЮKassa/СБП со сплитом, а реестры
   в УК — выгрузкой. Тогда Система «Город» остаётся источником начислений,
   а оплата идёт через нас.
