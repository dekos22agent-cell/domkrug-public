# Стенд домофонии: Hikvision и что с ним можно сделать

> Итог работы с реальным железом (06.11.2026). Отвечает на два вопроса: как
> открыть дверь из приложения и как получить вызов с панели. Оба решены;
> всё, что проверено и отвергнуто, тоже записано — чтобы не повторять.

## 1. Железо

| Устройство | Модель | Прошивка | Адрес | Роль |
|---|---|---|---|---|
| Вызывная панель №1 | DS-KD9633-E6 | V2.3.9 build 241016 | `192.168.2.108` | стенд |
| Вызывная панель №2 | DS-KD9403-E6 | V2.3.9 | `192.168.2.109` | стенд |
| Внутренний монитор | F-VI-3442IPWE1 | — | `192.168.2.125` | квартира |

Открытые порты у обеих панелей: **80** (ISAPI), **443**, **8000** (NetSDK),
**554** (RTSP). У монитора открыт **только 8000** — по HTTP он недоступен,
поэтому опрашивать его «как камеру» нельзя.

Учётка для интеграции — `admin`. **Отдельного пользователя завести нельзя:**
прошивка держит одну учётную запись (раздел 15). Это ограничение железа, а не
решение, и оно компенсируется сетевыми мерами (раздел 15.2).

## 2. Что работает: открытие двери

Штатный ISAPI, ничего патчить не нужно:

```
PUT /ISAPI/AccessControl/RemoteControl/door/<N>
<?xml version="1.0" encoding="UTF-8"?>
<RemoteControlDoor><cmd>open</cmd></RemoteControlDoor>
```

Успех:

```xml
<ResponseStatus>
  <statusCode>1</statusCode>
  <statusString>OK</statusString>
  <subStatusCode>ok</subStatusCode>
</ResponseStatus>
```

Доступные команды (из `/ISAPI/AccessControl/RemoteControl/door/capabilities`):
`open`, `close`, `alwaysOpen`, `resume`. Используем только `open`:
`alwaysOpen` держит дверь открытой до `resume`.

Номер реле (`N`) у панели бывает 1..2. Хранится в `access_points.provider_ref`.

Авторизация — HTTP **Digest** (`qop=auth`, MD5): первый запрос получает 401,
второй несёт хеш. Реализовано в `backend/src/modules/access/hikvision-provider.ts`.

Проверено end-to-end: из интерфейса приложения вызов доходит за ~800 мс,
в `access_events` пишется `ok`, реле щёлкает.

## 3. События: что отдаёт панель

### 3.1. `alertStream` — работает, но только про доступ

```
GET /ISAPI/Event/notification/alertStream
```

Отдаёт `multipart/mixed; boundary=MIME_boundary`, **тело части — JSON**
(хотя заголовок говорит multipart). При открытии панель вываливает всю
историю из своего буфера — в нашем случае события с мая 2026, полторы тысячи
записей.

Что приходит при работе с дверью:

| Событие | Значение |
|---|---|
| `major=5 sub=214`, `unlockType: "centerplatform"` | открытие через API (наш случай) |
| `major=5 sub=25` | дверь разблокирована |
| `major=5 sub=92` | дверь закрылась (ровно через 10 с после открытия) |
| `major=3 sub=1024` | служебное |

**Нажатие кнопки вызова в этом потоке не появляется никогда.**

### 3.2. `callStatus` — есть, но не отражает вызов

```
GET /ISAPI/VideoIntercom/callStatus?format=json
→ {"CallStatus": {"status": "idle"}}
```

Эндпоинт живой, но при реальном нажатии кнопки статус остаётся `idle`.
Опрос раз в секунду ничего не даёт.

Рядом есть `/ISAPI/VideoIntercom/callSignal/capabilities` — поддерживаются
`request`, `cancel`, `answer`, `reject`, `bellTimeout`, `hangUp`,
`deviceOnCall`. То есть отвечать и сбрасывать вызов можно, а узнать о нём — нет.

### 3.3. `httpHosts` — вебхук настраивается, но панель молчит

```
GET/PUT /ISAPI/Event/notification/httpHosts
```

Заполнили адрес, порт, путь, сохранили и через ISAPI, и через веб-интерфейс
(«Сеть → Дополнительно → Мониторинг HTTP»), перезагрузили. Панель не отправила
**ни одного** POST — ни на открытие двери, ни на вызов.

### 3.4. Вывод

Событие «нажата кнопка вызова» по HTTP/ISAPI на этой прошивке **недоступно**.
Остальные события доступа — доступны.

## 4. SIP: вызов доходит до клиента

### 4.1. Что развернули

**Asterisk 22.5.2** на Timeweb (`198.51.100.10`): транспорты UDP и TCP на
5060, абоненты `6001` (панель), `100` (клиент приложения) и добавочные 1–16.
Порт 5060 закрыт ufw для всех, кроме офисного IP.

### 4.2. Что обязательно настроить на панели

Четыре места, и пропуск любого ломает вызов **молча**:

| Где | Что |
|---|---|
| `Сеть → Конфигурация SIP-сервера` | галочка «Вкл.», адрес сервера, порт 5060, логин, пароль, номер |
| `Интерком → Настройки SIP-номеров` | **строка «номер комнаты → SIP-номер»** |
| `Интерком → Настройка сетевых параметров` | `IP-адрес сервера SIP` = адрес сервера |
| — | **перезагрузка панели** после ввода пароля |

Главная находка: **без записи в «Настройках SIP-номеров» вызов не уходит
вообще** — панель набирает номер комнаты, не находит его в таблице и обрывает
звонок локально с сообщением «сбой звонка». В сеть при этом не уходит ни один
пакет, и со стороны сервера это выглядит как «SIP не работает».

Запись, которая всё включила:

```
Номер комнаты: 100
SIP-номер:     100
```

Номер комнаты должен совпадать с `№ комнаты` из «Настройки сетевых
параметров»; SIP-номер — с абонентом в Asterisk.

### 4.3. Регистрация панели через ISAPI

```xml
<SIPServerList><SIPServer><id>1</id><Standard>
  <enabled>true</enabled>
  <proxy>198.51.100.10</proxy>
  <proxyPort>5060</proxyPort>
  <userName>6001</userName>
  <password>...</password>
  <displayName>6001</displayName>
  <authID>6001</authID>
  <expires>60</expires>
</Standard></SIPServer></SIPServerList>
```

Два подводных камня:

1. **Пароль не длиннее 16 символов** — иначе `400` без объяснений
   (лимит виден в `/ISAPI/System/Network/SIP/capabilities`).
2. **Нужна перезагрузка панели** — до неё `registerStatus=false` и ни одного
   пакета в сети, хотя конфиг сохранён.

Проверка на сервере:

```bash
sudo asterisk -rx 'pjsip show contacts'
# Contact: 6001/sip:6001@37.205.81.67:1946
```

### 4.4. Лог успешного вызова

```
INVITE sip:100@198.51.100.10:5060      ← панель звонит в комнату 100
SIP/2.0 401 Unauthorized                 ← Asterisk просит Digest
INVITE sip:100@198.51.100.10:5060      ← повтор с авторизацией
SIP/2.0 100 Trying
SIP/2.0 180 Ringing                      ← клиент зазвонил
```

На стороне клиента (baresip):

```
Call established: sip:6001@198.51.100.10
stream: incoming rtp for 'audio' established
audio: Set audio decoder: PCMA 8000Hz 1ch
```

На сервере:

```
PJSIP/6001-00000002   100@from-panel:2   Up   Dial(PJSIP/100,30)
PJSIP/100-00000003    (None)             Up   AppDial
2 active channels | 1 active call
```

`User-Agent` панели — `YATE/5.5.0` (SIP-стек Hikvision).

### 4.5. Тестовый клиент

Для проверки без телефона: `baresip` на сервере, абонент `100`,
`answermode=auto`. Рабочий конфиг и подводные камни — раздел 9.5.

## 5. NetSDK: попытка и её результат

Идея: события вызова через порт 8000, который открыт у обеих панелей.

- `HCNetSDK.dll` из iVMS-4200 — **32-битная**, наш Python 64-битный,
  загрузить нельзя.
- 64-битная нашлась в `C:\Program Files\VPWebControl\HCNetSDK.dll`:
  `NET_DVR_Init()` возвращает `true`, версия читается,
  `NET_DVR_Login_V40()` отдаёт **ошибку 29** (расшифровка — «No error»,
  то есть код не привязан к тексту в этой сборке).

Вывод: плагинная сборка урезана. Для рабочего пути нужен **официальный
64-битный HCNetSDK** с dev-портала Hikvision (бесплатная регистрация, архив
~200 МБ).

### 3.5. Приоритет вызова: запись закрыта, параллельность в данных есть (07.11.2026)

Проверяли гипотезу «в один уровень приоритета положить две цели — `["indoor","VoIP"]`».
Данные говорят, что так можно, запись говорит — нет.

Capabilities (`/ISAPI/VideoIntercom/callPriority/capabilities?format=json`):

```json
"unitType": { "maxSize": 3, "@opt": ["platform", "indoor", "VoIP"] },
"timeout":  { "@min": 30, "@max": 120 },
"priority": { "@min": 0, "@max": 3 }
```

Доказательство, что многоцелевой уровень в прошивке работает — **текущий же конфиг**:
уровень 1 содержит `["platform","indoor"]`, то есть две цели одновременно.

Что перепробовали на V2.3.9 build 241016:

| Попытка | Ответ |
|---|---|
| PUT JSON `["indoor","VoIP"]` | `400 badJsonContent` |
| PUT **точной копии** ответа панели | `400 badJsonContent` |
| Вложенный массив `[["indoor","VoIP"]]` | `400 badJsonContent` |
| `{"@opt": [...]}`, строка `"indoor,VoIP"` | `400 badJsonContent` |
| `id` у уровней, 2 и 3 уровня, строковые числа | `400 badJsonContent` |
| Обёртки `CallPriorityList`, `version` | `400 badJsonContent` |
| PUT XML `<CallPriority>` | `400 badURLFormat` |
| PUT по уровням `/callPriority/1` | `400 notSupport` (чтение тоже) |
| POST | `400 methodNotAllowed` |
| PUT c Basic-авторизацией | `401` (нужен Digest) |
| `callSignal` (`request`, `cancel`, `hangUp`) | `PUT` → `badJsonContent`, `GET`/`POST` → `methodNotAllowed` |

**Вывод:** даже собственный корректный конфиг панель не принимает — эндпоинт
только для чтения в этой сборке. Дело не в форме JSON и не в правах: мы
работаем под `admin`, чтение тех же ресурсов проходит.

В веб-интерфейсе панели страницы приоритета вызова **нет**: в `doc/app.js`
нет ни строки `VoIP`, ни `Priorities` — только ссылки на эндпоинт. Значит
приоритет выставлялся сторонним инструментом (iVMS-4200 / batch config).

**Следствие для продукта:** на этом железе параллельный вызов настраивается
только сторонним инструментом или другой прошивкой. Если не выйдет —
принимаем схему «VoIP первым» (приложение звонит сразу, монитор вторым).

**Важно перед пилотом:** текущая конфигурация отладочная (`VoIP` первым,
60 с). Для дома, где у жителя может не быть приложения, это означает, что
монитор зазвонит только через минуту. Пункт в списке перед запуском.

### 3.7. ПРОРЫВ: запись настроек возможна через сессионный логин (07.11.2026)

Раньше мы решили, что `callPriority` и `deviceCommunication` — «только для
чтения»: `PUT` отвечал `400 badJsonContent`. **Это было неверно.**

В коде веб-интерфейса панели (`doc/app.js`) часть ресурсов помечена
`security1: ["regPassword"]`. Для их записи нужен не обычный Digest, а
**сессионный логин**:

1. `GET /ISAPI/Security/sessionLogin/capabilities?username=admin&random=...`
   → `sessionID`, `challenge`, `iterations` (у нас 100), `isIrreversible: true`,
   `salt` (64 символа), `sessionIDVersion: 3`;
2. пароль считается формулой из их же `encodePwd`:
   ```
   h = sha256(login + salt + password)
   h = sha256(h + challenge)
   h = sha256(h) × (iterations − 2)
   ```
3. `POST /ISAPI/Security/sessionLogin` с XML → `200 OK`, `sessionTag`;
4. дальше запросы идут с заголовком `SessionID: <id>`.

**Результат: `PUT deviceCommunication` → `200 OK`.** Настройки записываются.
Инструмент: `scripts/hikvision.py` (команды `get`, `put`, `set-manage`,
`session`, `backup`).

#### Матрица допустимых комбинаций приоритета

Проверили шесть вариантов через сессию:

| Комбинация | Ответ |
|---|---|
| `[indoor, VoIP]` в уровне 0 | **400 badParameters** |
| `[VoIP, indoor]` (обратный порядок) | **400 badParameters** |
| `[indoor, VoIP, platform]` все три | **400 badParameters** |
| `[indoor, VoIP]` с timeout 30 | **400 badParameters** |
| `[platform, indoor]` в уровне 0 | **200 OK** |
| `[indoor]`, затем `[VoIP]` | **200 OK** |

**Вывод:** прошивка **сознательно запрещает** монитор и VoIP в одном уровне.
Одновременный звонок на монитор и в приложение этой моделью не поддерживается —
ни настройкой, ни API. Вендорская параллель — только `platform` + `indoor`,
то есть через платформу Hikvision (Hik-Connect), а не SIP.

#### Что это открывает

- Конфигурацию панели можно менять программно (пригодится для пилота:
  таймауты, приоритеты, адрес платформы).
- Параллель с приложением возможна только как «мы — платформа»: прописать
  `manage = наш сервер` и реализовать протокол платформы (ISUP/EHome).
  `Ehome`/`Integrate` на этой прошивке отвечают `notSupport`, поэтому
  протокол придётся выяснять по трафику при регистрации.
### 3.8. Параллельный вызов через callSignal (07.11.2026)

Панель запрещает `indoor`+`VoIP` в одном уровне, но умеет **поднимать вызов
на монитор по команде**. На этом собрана параллель:

```
курьер нажимает кнопку
        │
        ├─ панель звонит по VoIP (приоритет 0) ─────► Asterisk ──► приложение
        │                                              │
        │                                              └─ System(): ring-indoor.py
        │                                                        │
        └─ панель звонит монитору (callSignal indoor) ◄──────────┘
```

Оба вызова идут одновременно, разница — доли секунды.

**Команда вызова** (требует сессионного логина, см. §3.7):

```json
PUT /ISAPI/VideoIntercom/callSignal?format=json
{"CallSignal":{"cmdType":"request","target":{"unitType":"indoor","roomNumber":100}}}
→ 200 OK
```

Что выяснили про `callSignal`:

| Поле | Требование |
|---|---|
| `target` | обязательно объект (строка и массив отклоняются) |
| `unitType` | только `indoor`; `sip`, `voip`, `outdoor`, `manage` → `400 unitType` |
| `roomNumber` | **целое число**; строка → `not an interger` |
| `mappingRoomNumber` | не принимается, ошибка остаётся (поле не для записи) |
| `hangUp` | работает без target: `{"CallSignal":{"cmdType":"hangUp"}}` → 200 |
| сессия | живёт недолго: через несколько запросов `401`, нужен новый логин |

**Реализация:**

- `scripts/ring-indoor.py <комната>` — поднимает вызов на монитор;
  `ring-indoor.py hangup` — отпускает;
- диалплан `[from-panel]`: перед `Dial(PJSIP/${EXTEN})` вызывается скрипт,
  после — `hangup`, чтобы монитор не звонил до таймаута;
- учётные данные панели — `/etc/domkrug/panel.env` (`root:asterisk`, 640):
  Asterisk работает не под root и не должен читать `.env` проекта.

**Риск, который надо проверить кнопкой:** панель может ответить
`deviceBusy`, пока сама звонит по VoIP — тогда второй вызов не поднимется.
Скрипт делает до 8 попыток с паузой 1.5 с, но если панель занята всё время
разговора, монитор зазвонит только после его окончания. Проверка — только
живым нажатием: смотреть, звенит ли монитор и одновременно ли приходит
вызов в приложение.
## 6. Ловушки ISAPI, на которые уже наступили

1. **`alertStream` только по GET.** На POST — `400 methodNotAllowed`.
2. **Тело части — JSON**, хотя `Content-Type: multipart/mixed`.
3. **Одна сессия потока.** Пока предыдущее соединение не отпущено, следующий
   запрос получает `404` или `401`; ждать ~30 с.
4. **Буфер истории.** При подключении панель отдаёт всё накопленное — фильтруй
   по `dateTime`, иначе «события из мая».
5. **`401` без `WWW-Authenticate`.** Если панель отвергла хеш, она отвечает
   `401` **без** заголовка. Клиент обязан сбросить кэш nonce и сделать новое
   рукопожатие, иначе получает серию 401 и рискует блокировкой учётки.
6. **`httpHosts` ≠ `alertStream`.** Заполненный адрес ничего не значит:
   панель по нему не стучится.
7. **Поля SIP-страниц конфликтуют.** Сохранение «Настройки сетевых
   параметров» сбрасывает галочку «Вкл.» на «Конфигурации SIP-сервера»
   и обнуляет `IP-адрес сервера SIP`.
8. **`psql` и кириллица.** Русский литерал в SQL из консоли Windows уходит
   в cp866 → `invalid byte sequence for encoding "UTF8"`. Писать ASCII:
   `WHERE kind = 'wicket'`.
9. **iVMS-4200 ≠ веб-интерфейс.** Удалённая конфигурация показывает и пишет
   не то же самое, что родная веб-морда панели; расхождения видели дважды.

## 7. Что делать дальше

**Открытие калитки — готово.** Работает через ISAPI, уже в коде
(`hikvision-provider.ts`, ветка `office/stand-intercom`), проверено вживую.

**Вызов — инфраструктура готова.** Панель регистрируется на Asterisk, при
нажатии кнопки звонит в комнату и клиент принимает вызов с аудио (раздел 4).
Осталось соединить это с приложением — план в разделе 10.

**NetSDK больше не нужен.** Он был запасным путём на случай, если SIP не
пойдёт. SIP пошёл.

**Чего делать не стоит:**

- искать «магическую галочку» в SIP-настройках, если вызов не уходит: сначала
  проверьте **Настройки SIP-номеров** (раздел 4.2) — именно их отсутствие
  выглядит как неработающий SIP;

## 10. План интеграции звонка в приложение

Сейчас вызов доходит до Asterisk и до тестового клиента. Чтобы он всплывал
в интерфейсе жителя, нужны два куска.

### 10.1. Событие вызова в бэкенд (AMI)

Asterisk умеет отдавать события по **AMI** (Asterisk Manager Interface, TCP
5038). Бэкенду нужно знать о входящем вызове, чтобы показать «звонят в
калитку» и записать это в `intercom_calls`.

Порядок:

1. В `/etc/asterisk/manager.conf` включить AMI, слушать только `127.0.0.1`,
   завести пользователя с правами `read=call,system`, `write=call`.
2. В бэкенде — постоянное TCP-соединение к `127.0.0.1:5038`, логин, подписка.
3. На события `Newchannel` (`Context: from-panel`) — создать запись вызова и
   разослать уведомление через существующий модуль `notifications`.
4. На `Hangup` — закрыть запись, записать длительность и результат.

Это самый дешёвый шаг: без него звонок есть, но приложение о нём не знает.

### 10.2. WebRTC-клиент во фронтенде

Чтобы житель **слышал и говорил**, браузеру нужен WebRTC-транспорт:

1. В Asterisk включить `/etc/asterisk/http.conf` (HTTP) и
   `/etc/asterisk/pjsip.conf` транспорт `transport-wss` на 8089 с TLS.
   Сертификат — от Caddy (он уже держит домен `liviti.ru`).
2. Во фронтенде — `sip.js` (или `JsSIP`): подключение к
   `wss://liviti.ru:8089/ws`, регистрация абонентом `100`, приём `INVITE`.
3. Обратный прокси Caddy должен пропускать `/ws` на 8089.
4. **TURN обязателен**: офис за NAT, без relay часть медиа не пройдёт.
   Кандидат — `coturn` на том же сервере (порты 3478/udp, 5349/tls,
   49152–65535/udp).

Ориентир по времени: AMI — полдня, WebRTC + TURN — 1–2 дня, плюс правки UI.

### 10.3. Что проверить до начала

- Выдержит ли сервер (4 ГБ) Asterisk + TURN + приложение одновременно.
  Сейчас занято ~700 МБ, запас есть, но TURN под нагрузкой ест полосу.
- Нужен ли **видеозвонок**: панель отдаёт H.264 по RTP, браузеру понадобится
  транскодинг или согласование кодека (H.264 в WebRTC поддерживается, но не
  всеми браузерами одинаково).
- Политика хранения записей: писать ли аудио/видео звонков и на какой срок.

### 10.4. Ограничение стенда

Сейчас в Asterisk **один общий пароль** для всех абонентов (стенд). На боевом
объекте: свой пароль на абонента, отдельная учётка на панели (не `admin`),
ограничение по IP и регулярная ротация.


## 11. Туннель офис → сервер (06.11.2026)

Задача: прод-бэкенд на `198.51.100.10` должен доставать панели
`192.168.2.108` и `192.168.2.109`, которые живут в офисной сети за NAT.
Сервер их не видит — это блокировало включение двери на `liviti.ru`.

### 11.1. Почему SSH, а не WireGuard

WireGuard на Windows-клиенте требует маршрутизации пакетов в офисную LAN:
включить `IPEnableRouter`, настроить NAT, поправить реестр и перезагрузиться.
Всё это с правами администратора и легко ломается при обновлении.

Обратный SSH-туннель решает ту же задачу одной командой, без прав
администратора, и **не открывает серверу доступ ко всей офисной сети**:
проброшены ровно два порта к двум конкретным устройствам.

### 11.2. Как поднять

```powershell
powershell -ExecutionPolicy Bypass -File scripts\tunnel-office.ps1
```

Скрипт держит соединение и сам переподключается при обрыве. Параметры
(сервер, панели, порты) — аргументами, значения по умолчанию в файле.

На сервере после запуска:

```
127.0.0.1:18080  ->  192.168.2.108:80   (DS-KD9633-E6)
127.0.0.1:18081  ->  192.168.2.109:80   (DS-KD9403-E6)
```

### 11.3. Проверка

```bash
ss -ltn | grep -E '18080|18081'
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/ISAPI/System/deviceInfo
# 401 — устройство ответило, нужен пароль. Это и есть критерий готовности.
```

### 11.4. Что прописать в прод-`.env`

```ini
ACCESS_VENDOR_HOST=127.0.0.1:18080    # панель, которая открывает дверь
ACCESS_VENDOR_USER=<интеграционная учётка>
ACCESS_VENDOR_PASSWORD=<пароль>
ACCESS_VENDOR_HOLD_SECONDS=5
```

Для второй панели — отдельный провайдер или второй экземпляр с
`127.0.0.1:18081`.

### 11.5. Что осталось за кадром

Туннель живёт, пока запущен скрипт на офисной машине. Для постоянной работы
нужен автозапуск: Task Scheduler с триггером «при входе в систему» и
перезапуском при сбое. Для демонстрации достаточно запускать вручную.

## 14. WSS для браузера: порт 8089 (06.11.2026)

Чтобы звонок мог принять браузер, Asterisk должен отдавать SIP поверх
WebSocket с TLS.

### 14.1. Главная ловушка

Настройки `cert_file` и `priv_key_file` в секции `[transport-wss]` **
игнорируются**. В логе:

```
WARNING res_pjsip/config_transport.c: TLS certificate values ignored for
websocket transport as they are configured in http.conf
```

Сертификат для wss задаётся в `/etc/asterisk/http.conf`, там же и порт.
Из-за этого транспорт «есть» в `pjsip show transports`, но сокет не
открывается — и выглядит как «Asterisk не слушает 8089».

### 14.2. Рабочий `/etc/asterisk/http.conf`

```ini
[general]
servername=Asterisk
enabled=yes
bindaddr=127.0.0.1
bindport=8088
tlsenable=yes
tlsbindaddr=127.0.0.1:8089
tlscertfile=/etc/asterisk/certs/leaf.crt
tlsprivatekey=/etc/asterisk/certs/liviti.key
```

Сертификаты скопированы из хранилища Caddy:

```bash
sudo mkdir -p /etc/asterisk/certs
sudo cp .../liviti.ru/liviti.ru.crt /etc/asterisk/certs/liviti.crt
sudo cp .../liviti.ru/liviti.ru.key /etc/asterisk/certs/liviti.key
# для TLS нужен ТОЛЬКО листовой сертификат, без цепочки:
sudo awk '/BEGIN CERTIFICATE/{n++} n==1' liviti.crt > leaf.crt
sudo chown root:asterisk /etc/asterisk/certs/*; sudo chmod 640 /etc/asterisk/certs/*
```

### 14.3. Проверка

```bash
sudo ss -ltn | grep 8089                     # LISTEN 127.0.0.1:8089
curl -sk -o /dev/null -w '%{http_code}\n' https://127.0.0.1:8089/ws
# 426 Upgrade Required - эндпоинт живой, ждёт WebSocket
echo | openssl s_client -connect 127.0.0.1:8089 -servername liviti.ru 2>/dev/null \
  | openssl x509 -noout -subject -dates
# subject=CN=liviti.ru, срок до 03.02.2027
```

### 14.4. Что важно знать

- Слушаем **только loopback**: наружу отдаёт Caddy, проксируя `/ws`. Открывать
  8089 в ufw не нужно.
- Сертификат Caddy обновляет сам, но **копия в `/etc/asterisk/certs` не
  обновится**. До 03.02.2027 работает; перед этой датой нужен хук обновления
  (копирование после `caddy reload`) или переезд на чтение прямо из хранилища
  Caddy.
- Транспорт `[transport-wss]` в `pjsip.conf` всё равно нужен — он объявляет
  сам транспорт; но его `bind` и сертификаты фактически определяются
  `http.conf`.


## 15. Ограничение железа: одна учётная запись (06.11.2026)

Требование «интеграция не под `admin`» (раздел 7.2 `OFFICE-MACHINE.md`) на
этих панелях **невыполнимо**.

### 15.1. Что проверено

| Проверка | Результат |
|---|---|
| Веб-интерфейс: Конфигурация → Пользователь | только `admin`, кнопки «Добавить» нет |
| `GET /ISAPI/Security/users` | один пользователь |
| `PUT /ISAPI/Security/users/2` (пять вариантов схемы, пароли разной сложности) | `400` «Invalid Format» |
| `POST /ISAPI/Security/users` | `400` |
| `/ISAPI/Security/adminAccesses` | ограничивает протоколы и порты, но **не IP-адреса** |

Вывод: прошивка DS-KD9403-E6 / DS-KD9633-E6 поддерживает одну учётную запись,
иной схемы `User` для создания второй нет.

### 15.2. Компенсирующие меры

Раз отдельного пользователя не будет, риск закрывается сетью и гигиеной:

1. **Панель не смотрит в интернет.** Порт 80 доступен только на loopback
   сервера через SSH-туннель (`127.0.0.1:18081`); наружу открыт только Caddy
   с `/ws`.
2. **Пароль панели — в менеджере паролей и в `.env` прода.** В репозитории,
   переписке и документации его нет.
3. **Смена пароля при уходе любого, кто его видел.** Пароль засвечивался в
   переписке при настройке стенда — считать его компрометированным после
   ввода в эксплуатацию.
4. **Ограничение по сети на уровне роутера**, если появится: разрешить
   обращение к панели только с офисного мини-ПК.

### 15.3. Что это значит для боевого объекта

На реальном доме нужна панель, которая умеет несколько учётных записей с
разными правами (BAS-IP, Akuvox и подобные — это штатная возможность). На
Hikvision DS-KD9633/9403 интеграция будет ходить под `admin` — это надо
проговорить с заказчиком до закупки, а не после.


## 16. Приоритет вызова: задержка окна «Вам звонят» (06.11.2026)

Симптом: окно звонка появлялось в приложении почти через минуту. Причина на
панели, не в коде.

### 16.1. Как устроено

`GET /ISAPI/VideoIntercom/callPriority?format=json`

```json
{"CallPriority":{"Priorities":[
  {"targets":{"unitType":["platform","indoor"]},"priority":0,"timeout":60},
  {"targets":{"unitType":["VoIP"]},"priority":1,"timeout":60},
  {"targets":{"unitType":[]},"priority":2,"timeout":60}]}}
```

Три уровня: сначала платформа и монитор, потом VoIP (наш Asterisk), потом
пусто. Пока первый уровень не истечёт, вызов в приложение не уходит.

### 16.2. Что панель позволяет через API

Раздел **записываемый** — `PUT` с текущим содержимым возвращает `200`.
Ограничения проверены перебором:

| Изменение | Ответ |
|---|---|
| Поменять порядок групп (VoIP первым / монитор первым) | **200 OK** |
| `timeout` = 45 или 30 | **200 OK** |
| `timeout` = 29, 28, 25, 21, 20, 15, 10, 5 | 400 Invalid Content |
| `VoIP` в одной группе с `platform` / `indoor` / обоими | 400 |
| Группы `indoor+VoIP`, `platform+VoIP`, все три | 400 |
| `PUT` без `?format=json` | 400 |

**Вывод: минимум 30 секунд, и объединить монитор с VoIP нельзя.** Значит
одновременного звонка на монитор и в приложение эта прошивка не умеет.

### 16.3. Что выставлено сейчас

```json
{"CallPriority":{"Priorities":[
  {"targets":{"unitType":["platform","indoor"]},"priority":0,"timeout":30},
  {"targets":{"unitType":["VoIP"]},"priority":1,"timeout":60},
  {"targets":{"unitType":[]},"priority":2,"timeout":60}]}}
```

Монитор звонит 30 секунд, затем вызов уходит в приложение. Было 60 — стало
вдвое быстрее, и монитор продолжает работать.

Альтернатива, если приоритетнее мгновенный звонок в приложение: поставить
`VoIP` первым (`priority 0`). Тогда окно появляется сразу, но монитор в
квартире не звонит вообще — так было сделано на первом заходе, и это
справедливо забраковали.

### 16.4. Чего ждать от веб-интерфейса

Страница `Интерком → Приоритет вызова` показывает три строки с галочками
«Платформа» и «Внутренняя станция» — **чекбокса VoIP там нет**. Строка без
галочек и есть VoIP. Ползунок длительности, скорее всего, подчиняется той же
проверке на устройстве (минимум 30): пробовать 5 секунд имеет смысл только
если понадобится убедиться в этом окончательно.

### 16.5. Монитор в квартире: SIP не завёлся

Проверяли, можно ли позвать монитор `F-VI-3442IPWE1` (`192.168.2.125`)
параллельно с приложением — тогда панель могла бы отдавать вызов только в
VoIP, без ожидания.

Что сделали:

- завели в Asterisk абонента `101`;
- заполнили на мониторе `Интерком → Конфигурация SIP-сервера` (сервер, порт,
  логин, пароль, номер);
- заполнили `IP-адрес сервера SIP` в «Настройке сетевых параметров» —
  там было `0.0.0.0`, как когда-то у панели;
- перезагрузили монитор.

Результат: **статус «Регистрация отменена», ноль пакетов в сети** (проверено
`tcpdump` на сервере). `pjsip show contacts` монитор не показывает.

Ещё деталь: `Интерком → Настройки SIP-номеров` на мониторе открывает таблицу
**внешних устройств** (серийный номер, IP, маска, шлюз) — это список
домофонов для вызова, а не регистрация самого монитора. Заполнять её для
нашей задачи бессмысленно.

**Вывод:** у этой модели SIP работает только внутри экосистемы Hikvision.
Параллельного звонка на монитор и в приложение не будет — остаётся
компромисс 30 секунд из 16.3.

### 16.6. Откат

Исходная настройка: `/root/panel-callpriority-backup.json` на сервере.
Вернуть — `PUT` этим файлом на тот же адрес с `?format=json`.
