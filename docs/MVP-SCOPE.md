# Границы MVP и критерии приёмки

**Версия:** 1.0 · **Дата:** 02.11.2026 · **Статус:** на согласовании

---

## 1. Что такое MVP в этом проекте

MVP — версия, которую **можно показать 2–3 УК и дать им поработать неделю** без ежедневного участия разработчика.

Это **не** «демо-картинки» и **не** «половина системы». Это рабочий сквозной процесс:

> житель создаёт заявку → диспетчер её видит → назначает исполнителя → исполнитель выполняет и закрывает → житель видит результат

Если этот цикл работает устойчиво — MVP состоялся. Всё остальное — обвязка.

---

## 2. Что входит в MVP

### 2.1. Пользователи и доступ
- Регистрация жителя с согласием на обработку ПДн.
- Вход/выход, восстановление пароля по e-mail.
- Привязка жителя к квартире с подтверждением админом/диспетчером УК.
- 5 ролей, права по матрице `RBAC.md`.
- Изоляция УК (доказана тестами).

### 2.2. Структура
- УК → ЖК → дома → подъезды → этажи → квартиры.
- Создание/редактирование вручную.
- Импорт квартир из CSV (иначе заводить 200 квартир руками — боль).

### 2.3. Заявки
- Создание жителем (с фото), создание диспетчером по телефону.
- Категории, срочность, SLA-срок, подсветка просрочки.
- Статусы по решению C: исполнитель закрывает сразу, с обязательным результатом и фото.
- Назначение/переназначение исполнителя.
- История статусов (кто, когда, из какого в какой).
- Комментарии, в т.ч. служебные (невидимые жителю).
- «Проблема не решена» → новая заявка со ссылкой на исходную.

### 2.4. Информирование
- Внутрисистемные уведомления (колокольчик + счётчик).
- E-mail уведомления о смене статуса.
- Новости/объявления по уровням: УК, ЖК, дом. Экстренные — с пометкой.

### 2.5. Кабинеты
- **Житель:** главная, мои заявки, создание заявки, новости, профиль.
- **Диспетчер:** инбокс с фильтрами, карточка заявки, назначение, привязки на подтверждение.
- **Исполнитель:** мои заявки, смена статуса, фото результата, закрытие.
- **Админ УК:** структура, сотрудники, категории, новости.

### 2.6. Техническое
- Docker Compose для запуска одной командой.
- Миграции БД, сид демо-данных.
- Аудит критичных действий.
- Тесты: изоляция УК, права, переходы статусов.
- Адаптив (телефон/планшет/ПК), PWA-манифест.

## 3. Что НЕ входит в MVP (явно)

| Функция | Почему нет | Когда |
|---|---|---|
| Приборы учёта и показания | Отдельный процесс, не блокирует заявки | v2 |
| Начисления, платежи, квитанции | Платёжные риски, интеграции, 152-ФЗ | v2 |
| АСДС как отдельный модуль | Дублирует заявки; аварийность — флаг | v2 |
| Нативные iOS/Android | PWA покрывает MVP | v2 |
| Push-уведомления | На iOS ограничены, на Android — v2 | v2 |
| Отчёты и аналитика | Нужны данные, которых пока нет | v2 |
| ENVIRO, домофония, СКУД, видеонаблюдение | Нет API/договоров | v3 |
| Имперсонация platform_admin | Риск, не нужен на пилоте | v3 |
| Роль «Руководитель УК» (интерфейс) | На пилоте это админ УК | v2 |
| Маркетплейс, бронирования, зарядки | Не влияют на ядро | v3+ |

## 4. Критерии приёмки

Проверяемые вручную, по шагам. MVP принят, если **все** пункты проходят на чистой установке из репозитория.

### 4.1. Сквозной сценарий (главный)

| # | Шаг | Ожидаемый результат |
|---|---|---|
| 1 | Житель регистрируется, указывает квартиру | Заявка на привязку в статусе «ожидает» |
| 2 | Админ УК подтверждает привязку | Житель видит свой адрес, кнопка «Создать заявку» активна |
| 3 | Житель создаёт заявку: категория «Сантехника», срочность «Высокая», фото, телефон | Заявка сохранена, номер присвоен, SLA-срок рассчитан |
| 4 | Диспетчер открывает инбокс | Заявка в списке, помечена как новая |
| 5 | Диспетчер принимает и назначает исполнителя | Статус «Назначен исполнитель», исполнитель видит заявку у себя |
| 6 | Исполнитель берёт в работу | Статус «В работе», житель получил уведомление |
| 7 | Исполнитель ставит «Ожидает материалов», пишет служебный комментарий | Житель **не видит** служебный комментарий |
| 8 | Исполнитель прикладывает фото результата и закрывает с комментарием | Статус «Закрыта», обязательные поля не дали закрыть пустыми |
| 9 | Житель открывает заявку | Видит статус, фото результата, комментарий исполнителя |
| 10 | Житель нажимает «Проблема не решена» | Создана новая заявка со ссылкой на исходную |

### 4.2. Изоляция и права

| # | Проверка | Ожидаемый результат |
|---|---|---|
| 11 | Житель УК-А открывает заявку УК-Б по прямому ID | 404 |
| 12 | Диспетчер УК-А не видит заявок УК-Б в списке | Пусто |
| 13 | Исполнитель видит только свои назначенные заявки | Да |
| 14 | Исполнитель не может открыть чужую заявку | 404 |
| 15 | Житель без подтверждённой привязки не может создать заявку | 403 + понятное сообщение |
| 16 | Житель не видит служебные комментарии | Да |
| 17 | `platform_admin` не может открыть заявку | 403 |
| 18 | Диспетчер не может закрыть заявку | 403 |
| 19 | После деактивации сотрудника его токен не работает | 401 |

### 4.3. Интерфейс

| # | Проверка | Ожидаемый результат |
|---|---|---|
| 20 | Главная жителя на телефоне (375px) | Читаемо, кнопки не мельче 44px |
| 21 | Форма заявки на телефоне | Заполняется без горизонтальной прокрутки |
| 22 | Инбокс диспетчера на ПК (1440px) | Таблица/список читаемы, фильтры работают |
| 23 | Просроченная по SLA заявка | Визуально выделена |
| 24 | Пустые состояния | Понятный текст, а не пустой экран |

### 4.4. Запуск и данные

| # | Проверка | Ожидаемый результат |
|---|---|---|
| 25 | `docker compose up -d` на чистой машине | Всё поднимается, миграции применяются |
| 26 | `npm run db:seed` | Демо-данные: 2 УК, 3 дома, 12 квартир, 8 пользователей, 10 заявок |
| 27 | Демо-данные не содержат реальных ПДн | Проверено вручную |

## 5. Демо-данные (сид)

Обязательный состав — иначе показывать нечего:

**УК-1 «Дом-Сервис»** (основная для демонстрации)
- ЖК «Северный» → дом «ул. Ленина, 1» → 3 подъезда → 9 этажей → 12 квартир
- Сотрудники: админ, диспетчер, 2 исполнителя (сантехник, электрик)
- Жители: 4 подтверждённых, 1 ожидающий подтверждения

**УК-2 «ЖилКомфорт»** (для проверки изоляции)
- ЖК «Южный» → дом «ул. Мира, 5» → 6 квартир
- Сотрудники: админ, диспетчер
- Жители: 2 подтверждённых

**Заявки:** 10 штук в разных статусах, из них:
- 2 новые (одна аварийная),
- 1 просроченная по SLA,
- 1 в работе с фото,
- 1 ожидает материалов,
- 3 закрытые (разные категории),
- 1 отклонённая,
- 1 повторная (со ссылкой на закрытую).

**Все имена/телефоны — вымышленные.** Телефоны в диапазоне `+7 900 000-XX-XX`, чтобы ничей реальный номер не совпал.

**Демо-пароли** — в `README.md`, одинаковые для всех демо-пользователей (`Demo1234!`), с явной пометкой «только для локальной демонстрации».

## 6. Определение готовности (definition of done)

Фича считается готовой, когда:

1. Работает по описанному сценарию.
2. Есть тест на изоляцию (если трогает данные УК).
3. Есть тест на права (если трогает роли).
4. Обновлён `PROGRESS.md`.
5. Изменения закоммичены с описанием «что и почему».
6. Не сломаны ранее проходящие сценарии (ручной прогон 10 шагов из 4.1).

**Чего НЕ требует definition of done на MVP:** покрытие тестами 80%, идеальный UI, оптимизация запросов, документация каждой функции. Это v2.

## 7. Оценка объёма

| Блок | Сложность | Комментарий |
|---|---|---|
| Каркас (Docker, миграции, конфиг) | средняя | Разово |
| Аутентификация и роли | средняя | Основа всего |
| Структура домов + импорт | низкая | Много похожего кода |
| Заявки (backend) | **высокая** | Ядро: статусы, SLA, права, история |
| Кабинет жителя | средняя | 5 экранов |
| Кабинет диспетчера | **высокая** | Инбокс, фильтры, карточка |
| Кабинет исполнителя | низкая | 3 экрана |
| Привязки жителей | низкая | Простой флоу |
| Новости, уведомления | низкая | |
| Адаптив и PWA | средняя | Много мелочей |
| Тесты | средняя | Изоляция и права — обязательно |

**Итого:** ядро — заявки и права. Всё остальное — вокруг них. Поэтому начинаем с каркаса → auth → структура → **заявки** → кабинеты → обвязка.

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Объём расползается («а давайте ещё счётчики») | **высокая** | Этот документ — фильтр. Новое требование = v2, если не блокирует сквозной сценарий |
| Диспетчеры не примут интерфейс | средняя | Показать инбокс на 3-й день разработки, не в конце |
| Демо-данные не отражают реальность УК | средняя | Взять у одной УК список реальных категорий (без ПДн) |
| Тесты изоляции забыты в спешке | средняя | Они в definition of done, а не «потом» |
| Один разработчик + две машины = расхождение контекста | средняя | `PROGRESS.md` после каждого этапа |

## 9. Что дальше после MVP

Порядок v2 — по результатам пилота, не по ТЗ. Предварительно:
1. То, на что жалуются диспетчеры в первую неделю.
2. Отчёты для руководителя УК (без них УК не платит).
3. Счётчики (если попросят).
4. АСДС (если аварий много).
5. Платежи — последними: самая дорогая и рискованная часть.
