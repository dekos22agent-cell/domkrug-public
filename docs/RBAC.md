## 2. Соглашение по именованию прав

```
<ресурс>.<действие>
```

- Ресурс — в единственном числе: `ticket`, `building`, `resident_binding`.
- Действие — глагол: `view`, `create`, `update`, `archive`, `assign`, `close`.
- Иерархия через точку для уточнения: `ticket.view.own`, `ticket.view.all`.

**Правило:** право отвечает на вопрос «какое действие разрешено», и **ничего не знает** о том, к каким именно строкам оно применимо. Ограничение по строкам (своя УК, своя заявка) — отдельный механизм, «область данных» (раздел 5).

Это разделение принципиально: `ticket.view.all` + область «своя УК» = диспетчер видит все заявки своей УК. Одно право, разные области — не нужно заводить по праву на каждую комбинацию.

## 5. Область данных (data scope)

Право отвечает «что можно». Область отвечает «над какими строками».

| Роль | Область | Что видит |
|---|---|---|
| `platform_admin` | Платформа | Только список УК и платформенный аудит. **Без заявок, жителей и ПДн** |
| `uk_admin` | `tenant_id = свой` | Всё в своей УК |
| `dispatcher` | `tenant_id = свой` | Все заявки УК, квартиры, жители (ФИО, телефон) — для связи |
| `executor` | `tenant_id = свой` **И** `assigned_to = он` | Только назначенные заявки. Телефон жителя — пока заявка не закрыта |
| `resident` | `user_id = он` **И** `status = confirmed` | Свои привязки, свои квартиры, свои заявки |

### 5.1. Реализация области

**Уровень 1 — middleware.** После проверки JWT в контекст запроса кладётся:

```
{ userId, tenantId, roles[], permissions[] }
```

`tenantId` берётся **только** из токена. Если роль `resident` — `tenantId` может быть NULL (житель не привязан к УК глобально), тогда область строится по `resident_bindings`.

**Уровень 2 — guard на маршруте.** `requirePermission('ticket.view.all')` — 403, если права нет.

**Уровень 3 — репозиторий.** Каждый метод принимает scope:

```ts
ticketRepo.list({ tenantId, scope: { kind: 'assigned', userId } })
```

Методов «без scope» в репозитории **не существует**. Это не соглашение, а архитектурное ограничение: нельзя случайно вызвать «всё».

### 5.2. Проверка «своей» заявки для жителя

Житель видит заявку, если:

1. `tickets.created_by = userId`, **или**
2. `tickets.apartment_id` входит в его подтверждённые привязки **и** `tenant_id` совпадает.

Оба условия проверяются в репозитории, не в контроллере.

## 6. Особые случаи

### 6.1. `platform_admin` и изоляция УК

ТЗ v1.1 п. 2: «данные одной УК не видны другой УК, **включая системному администратору платформы** — кроме специально предусмотренных технических сценариев с журналированием».

**Реализация:**

- `platform_admin` **не имеет** прав `ticket.*`, `apartment.view`, `resident_binding.*` — физически не может открыть заявку;
- для поддержки (клиент жалуется «не работает») — **режим имперсонации**: администратор платформы запрашивает временный доступ к УК, действует **от имени** администратора этой УК, всё пишется в `audit_log` с `action = 'platform.impersonate'`;
- имперсонация — отдельная фича, **не в MVP**. На пилоте поддержку оказываем через администратора УК.

**Это позиция, а не недоработка:** «супер-админ, который видит всё» — главный риск утечки и главный вопрос на любом серьёзном тендере УК.

### 6.2. Самообслуживание жителя

Действия, которые житель делает **без отдельного права** (они про себя, не про данные УК):

- регистрация;
- создание заявки на привязку к квартире (`resident_bindings` в статусе `pending`);
- редактирование своего профиля;
- смена пароля;
- отзыв своей привязки.

Проверка в этих случаях — «объект принадлежит текущему пользователю», а не «есть право X».

### 6.3. Исполнитель и персональные данные

Исполнитель видит телефон жителя — иначе не сможет позвонить и согласовать время. Но:

- видит **только по назначенным заявкам**;
- после закрытия заявки телефон скрывается из интерфейса (остаётся в БД для истории и аудита);
- список жителей дома исполнителю **недоступен**.

### 6.4. Комбинирование ролей

Один пользователь может иметь несколько ролей (например, `dispatcher` + `executor` в маленькой УК — это реальность). **Права объединяются (union).**

Область данных при этом берётся **максимальная из разрешённых** — но только по тем правам, которые есть. Пример: диспетчер-исполнитель видит все заявки УК (как диспетчер), а не только свои.

### 6.5. Смена ролей и увольнение

- Деактивация сотрудника (`staff.is_active = false`) → сессии инвалидируются, `user_roles` для этой УК отзываются.
- История заявок исполнителя **сохраняется**, назначения не переписываются.
- Заявки, которые были у уволенного в работе, попадают в список «требуют переназначения» у диспетчера.

## 7. Где проверяется доступ

| Слой | Что проверяет | Что НЕ проверяет |
|---|---|---|
| Middleware | Валидность JWT, срок, блокировка пользователя | Права |
| Guard (маршрут) | Наличие права (`requirePermission`) | Принадлежность объекта |
| Сервис | Бизнес-правила (нельзя закрыть без `resolution_note`) | Права и область |
| Репозиторий | Область данных (`tenant_id`, `assigned_to`, привязки) | Права |

**Правило:** проверка прав и проверка области — **разные слои**. Смешивать нельзя: иначе получим «право проверено в репозитории» и дыры там, где репозиторий вызвали напрямую.

## 8. Тесты, которые обязательны (не «потом»)

Определение готовности любой фичи с данными — эти тесты зелёные:

| # | Тест |
|---|---|
| 1 | Житель УК-А не видит заявки УК-Б (ни в списке, ни по прямому ID → 404) |
| 2 | Диспетчер УК-А не видит заявок УК-Б |
| 3 | Исполнитель видит **только** назначенные ему заявки |
| 4 | Исполнитель не может открыть чужую заявку по ID → 404 (не 403 — не подтверждаем существование) |
| 5 | Житель не может создать заявку без подтверждённой привязки → 403 |
| 6 | Житель не может создать заявку на чужую квартиру → 403 |
| 7 | Житель не видит служебные комментарии (`is_internal = true`) |
| 8 | `platform_admin` не может открыть заявку → 403 |
| 9 | Диспетчер не может закрыть заявку (`ticket.close`) → 403 |
| 10 | Исполнитель не может отклонить заявку (`ticket.reject`) → 403 |
| 11 | Житель не может удалить чужой комментарий → 403 |
| 12 | После деактивации сотрудника его токен не работает |

**Формулировка «404, не 403»** — намеренная: 403 подтверждает, что объект существует. Для чужих тенантов отвечаем 404.

|---|---|
| СКУД | `access_rights.can_open` |
| Видео | `can_video` |
| Счётчики | `can_meters` |
| Заявки | `can_tickets` (`hasConfirmedBinding`) |
| Оплата (фронтенд) | `can_finance`; серверные начисления появятся с биллингом |
| Члены квартиры | `can_manage` |

Проверки идут **на сервере**: интерфейс лишь скрывает то, что и так недоступно.

### 11.4 Гостевой доступ

Гость не имеет ни ролей, ни прав платформы. У него есть только членство
с правами и токен типа `guest`; `/auth/me` и `/resident/*` для него закрыты.
Права перечитываются из базы на каждом запросе — отзыв и истечение срока
действуют немедленно.
