# Ответ на внешнее ревью безопасности (08.11.2026)

Ревью: Claude, ~треть бэкенда плюс выборочный фронтенд, без запуска кода.
Ниже — что подтвердилось, что исправлено и что остаётся блокером реального
пилота. Ссылки на файлы — в текущем `main`.

## Исправлено

### 1. Выход падал в проде (рекурсия)

Подтвердилось, и это был наш баг: `clearRefreshCookie` вызывала саму себя
при заданном `COOKIE_DOMAIN`, поэтому `/auth/logout`, смена пароля и ветки
`/refresh` отдавали 500. Исправлено в
`backend/src/modules/auth/routes.ts`; проверено отдельным инстансом с
`COOKIE_DOMAIN=.liviti.ru` — logout отдаёт 204. Тесты не ловили, потому что
локально домен не задан; теперь это проверяется вручную при релизе.

### 2. API слушал все интерфейсы

На проде было `0.0.0.0:3000` (снаружи порт закрывал файрвол, но это второй
рубеж, а не единственный). Теперь `APP_HOST` по умолчанию `127.0.0.1`;
наружу смотрит только Caddy. `trustProxy` остаётся, потому что X-Forwarded-For
приходит от Caddy на loopback. Проверка после деплоя: `ss -ltnp` показывает
`127.0.0.1:3000`.

### 3. Небезопасный JWT_SECRET по умолчанию

`JWT_SECRET` теперь обязателен всегда, а значение из `.env.example`
отвергается, пока явно не задан `ALLOW_INSECURE_DEV_SECRET=true`. Локальный
секрет заменён на случайный; на проде был свой (64 символа), `NODE_ENV=production`.
`.env.example` больше не содержит рабочей заглушки.

### 4. Перебор гостевых кодов и предсказуемый генератор

- `authenticateByCode` больше не перебирает все коды: миграция
  `023_code_lookup.sql` добавляет индексируемый HMAC-ключ
  `access_code_lookup`, поиск идёт одним `SELECT`, bcrypt проверяет только
  найденную строку.
- `randomCode` использует `crypto.randomInt`, а не `Math.random`.
- Старые коды бэкфиллятся `npm run db:backfill-code-lookup`; deploy выполняет
  его автоматически.
- HMAC-ключ может быть отдельным (`CODE_SECRET`), иначе берётся `JWT_SECRET`.

Замечание про обратимое шифрование кода (владелец видит его в списке) остаётся:
ключ шифрования по-прежнему выводится из `JWT_SECRET`. Для реального пилота
нужно либо задать отдельный `CODE_SECRET`, либо показывать код только один раз.
Это осознанный компромисс ради функции «продиктовать код».

### 5. Неатомарное обновление refresh

Два одновременных `/refresh` могли создать две живые сессии. Теперь сессия
забирается атомарно:

```sql
UPDATE sessions SET revoked_at = now()
WHERE id = $1 AND revoked_at IS NULL AND expires_at > now()
```

Победитель создаёт новую сессию; проигравший получает 401. Недавняя ротация
(до 5 секунд) не закрывает сессию победителя — это две вкладки, а не кража;
старый токен старше 5 секунд закрывает все сессии. Есть тест
`два одновременных refresh не создают две живые сессии`.

### 6. Блокирующий scrypt и перечисление по времени

Добавлены асинхронные `hashPasswordAsync`/`verifyPasswordAsync`; вход,
регистрация, смена пароля и гостевой код больше не блокируют event loop.
Для несуществующего пользователя выполняется проверка против фиктивного
хеша, чтобы время ответа не отличалось от неверного пароля.

### 7. Приглашения по телефону

Автоматическая выдача доступа убрана. Приглашённый может зарегистрироваться,
но доступ включается только после кнопки «Подтвердить» у владельца
(`POST /resident/members/:id/confirm`). До подтверждения человек не видит
квартиру, двери, камеры и заявки. Приглашения активируются после пароля и
2FA, а не до проверки пароля.

Это **не заменяет проверку номера SMS-кодом**: злоумышленник всё ещё может
зарегистрироваться с чужим номером и ждать, пока владелец подтвердит. Но
молчаливой выдачи прав больше нет. Для реального пилота нужен SMS-шлюз или
звонок с кодом.

### 8. Публичная копия и инфраструктура

Публичная копия для аудита (`domkrug-public`) собирается снимком без истории;
из неё убраны боевые секреты, а адрес сервера и детали доступа редактируются.
Основной репозиторий остаётся приватным. Это не отменяет того, что публичная
копия — отдельный риск: её нужно удалить после аудита.

### 9. Прочее

- PDF-вложения отдаются с `Content-Disposition: attachment`; фото — inline.
- Неиспользуемый S3-сервис из `docker-compose.yml` удалён: он слушал все
  интерфейсы без авторизации.
- CI: workflow подготовлен и описан в `docs/CI.md`. Автоматический запуск
  пока не включён: у текущего PAT нет `workflow`-scope, GitHub отклоняет
  push файла `.github/workflows/ci.yml`. Нужно добавить через веб-интерфейс
  или токеном с этим scope.

## Остаётся блокером реального пилота

1. **Проверка телефона.** Нужен SMS/звонок до привязки приглашений. Сейчас
   есть только подтверждение владельцем.
2. **SIP: один абонент на всех.** `video/routes.ts` отдаёт общий пароль
   Asterisk любому вошедшему жителю. Нужны отдельные абоненты на квартиру и
   выдача учётных данных только своим.
3. **2FA для персонала.** Остаётся необязательным; нет защиты от повторного
   TOTP-кода и блокировки по аккаунту (лимиты — по IP). Секрет TOTP лежит в
   БД открытым текстом.
4. **RLS.** Изоляция УК держится на проверках в маршрутах. Для реального
   пилота нужен `ROW LEVEL SECURITY` как второй рубеж, особенно для
   `addComment` и новых эндпоинтов.
5. **Видеопоток.** `stream_url` отдаётся как есть, `expiresAt` не ограничивает
   ссылку. Нужны подписанные короткоживущие URL.
6. **СНИЛС.** Лежит в БД открытым текстом и целиком возвращается в `/auth/me`.
   Нужно шифрование и маска в ответе.
7. **Ключ кодов.** Отдельный `CODE_SECRET` поддержан, но на проде пока
   используется `JWT_SECRET`; при утечке JWT владелец увидит все коды.

## Контекст, который ревью не мог проверить

- `NODE_ENV=production`, `JWT_SECRET` — свой, 64 символа, не из примера.
- HTTPS на всех трёх хостах работает через Caddy; `www` редиректит.
- API был на `0.0.0.0`, но внешний порт 3000 закрыт файрволом; теперь API
  слушает только loopback.
- PostgreSQL слушает только `127.0.0.1`.

## Дополнение по второму ревью (ChatGPT, 08.11.2026)

Второе ревью читало уже текущий код. Часть High-пунктов совпала с уже
зафиксированными блокерами (SIP, видео, СНИЛС, 2FA, RLS, SMS), но нашлись
и новые полезные замечания — они исправлены:

- **Advisory lock миграций.** `pg_advisory_lock` брался через `pool.query()`,
  а миграции шли через другое соединение пула. Теперь один `PoolClient`
  держит lock, выполняет миграции и снимает его.
- **Checksum миграций.** В `schema_migrations` добавлена SHA-256 сумма файла;
  изменение уже применённой миграции останавливает деплой.
- **`trustProxy: true`.** Заменён на явный список `127.0.0.1`/`::1`.
- **`addComment` без tenant_id.** Проверка заявки и запись комментария теперь
  в одной транзакции и с `tenant_id`; уведомления тоже фильтруются по УК.
- **Ключ шифрования из JWT_SECRET.** Добавлен `DATA_ENCRYPTION_KEY` и формат
  `v2.`; старые значения без версии читаются ключом из JWT, поэтому переход
  не ломает уже выданные коды. Полноценная ротация ключей — отдельная задача.
- **`.env.example`.** Убраны неиспользуемые S3/SMTP/rate-limit переменные,
  добавлены `STORAGE_DIR`, `CORS_ORIGINS`, `DATA_ENCRYPTION_KEY`.
- **Документация.** Добавлен `docs/DOCS-STATUS.md`; `DB-SCHEMA.md` помечен
  как исторический проект, `API-CONTRACT.md` — как целевой контракт.

Про CORS: в production все три фронта ходят на относительный `/api` своего
же origin, поэтому CORS не участвует и одной `APP_URL` достаточно. Для
будущего отдельного api-поддомена добавлен явный `CORS_ORIGINS`.

Остальные пункты второго ревью (SIP, видео, СНИЛС, 2FA, RLS, SMS) остаются
в списке блокеров ниже — они не были «закрыты» косметически.
