# Разделение приложений: житель и УК

Статус: план, 07.11.2026.
Цель: два клиента (житель и УК) поверх одного бэкенда и одной модели данных.

## 1. Зачем

Сейчас один SPA обслуживает обе роли: в `Layout` переключается навигация, в
страницах проверяется `isStaff`, а карточка заявки одна на всех. Это уже дало
два класса ошибок: диспетчер не видел фото (запрос уходил на жительский
эндпоинт) и любые правки УК рискуют сломать жителя.

Разделение даёт:

- разные интерфейсы под разные задачи и устройства (телефон против монитора);
- независимые релизы: правка для УК не трогает приложение жителей;
- меньше прав-ошибок: житель физически не попадает в интерфейс УК;
- white-label: сайт УК на своём поддомене;
- чистую модель доступа к ПДн: у сотрудников УК отдельные учётки и аудит.

## 6. Риски

| Риск | Как снимаем |
|---|---|
| Карточка заявки окажется «двумя приложениями в одном файле» | Разделяем на фазе 2, до создания `apps/staff` |
| Дублирование компонентов | Пакет `ui` создаём первым, до разделения |
| Два фронта разъедутся по версиям API | Общий `packages/shared`, версионируем вместе с бэкендом |
| Пользователи потеряют закладки | Редиректы и сохранение путей |
| Долгая фаза 1 без видимого результата | После каждой фазы продукт работает |

## 7. С чего начинаем

**Фаза 1, задача 1:** npm workspaces и вынос `packages/shared`.

Почему не с карточки заявки и не с нового приложения: пока общий код лежит
внутри `frontend/src`, любое разделение превращается в копирование файлов и
ручное правление импортов. Сначала общий слой — потом разрез.

Порядок внутри фазы 1:

1. `package.json` в корне с `workspaces`.
2. `packages/shared`: `api`, `auth`, `types`, `format`, хуки.
3. `packages/ui`: компоненты и их CSS.
4. Текущий `frontend` переезжает в `apps/resident` и импортирует из пакетов.
5. Сборка, линт, тесты — зелёные. Коммит.


## 8. Переезд на поддомены (когда появятся DNS-записи)

Нужны три A-записи на `198.51.100.10`: `app`, `uk`, `*`.

Порядок:

1. Дождаться, пока `getent hosts app.liviti.ru` и `uk.liviti.ru` вернут адрес сервера.
2. Собрать клиенты под поддомены: `DEPLOY_TARGET=subdomains bash scripts/deploy.sh`.
3. Включить блоки Caddy: `bash scripts/enable-subdomains.sh` — скрипт сам проверит
   DNS, сделает бэкап, добавит блоки, превратит `/app` и `/uk` в редиректы и
   перезагрузит Caddy.
4. Проверить `https://app.liviti.ru/`, `https://uk.liviti.ru/` и вход в обоих.

Откат: `cp /etc/caddy/Caddyfile.bak.* /etc/caddy/Caddyfile && systemctl reload caddy`,
затем `bash scripts/deploy.sh` (режим `paths`).

**Wildcard `<ук>.liviti.ru`** — следующий шаг: нужен блок Caddy с `on_demand_tls`
и endpoint-валидатор в бэкенде, иначе сертификат на произвольный поддомен не
выпустить.
